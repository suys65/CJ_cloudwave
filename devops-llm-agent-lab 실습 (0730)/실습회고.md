# LLM 에이전트가 쿠버네티스 장애를 진단한다면 — DevOps LLM Agent Lab

## 들어가며

이 실습은 GitOps로 관리되는 쿠버네티스 클러스터에 실제 장애를 일으키고, Bedrock 기반 LLM 에이전트가 도구(tool) 호출을 통해 원인을 진단한 뒤 사람의 승인을 받아 리포트를 발송하는 워크플로우를 검증한다.

핵심은 전 과정이 실제 인프라 위에서 동작한다는 점이다. `break_it.py`는 매니페스트를 Git에 실제로 커밋하고, ArgoCD가 이를 클러스터에 반영하며, pod는 실제로 실패 상태에 빠진다. 에이전트 역시 고정된 로그를 읽는 게 아니라 Kubernetes API를 직접 호출해 현재 상태를 조회한다.

---

## 핵심 개념

### GitOps / ArgoCD

GitOps는 클러스터의 원하는 상태(desired state)를 Git 저장소에 선언하고, 컨트롤러가 이를 클러스터의 실제 상태(actual state)에 지속적으로 동기화하는 운영 모델이다. 이 실습의 Git 서버는 경량 자체 호스팅 Git인 **Gitea**, 동기화 컨트롤러는 **ArgoCD**를 사용한다.

```
매니페스트 변경 → Git 커밋 → ArgoCD 변경 감지 → 클러스터 적용 → Pod 상태 변화
```

장애 주입도 동일한 파이프라인을 통과한다. 즉 "무엇이 언제 바뀌었는가"가 항상 Git 커밋 이력에 남으므로, 장애 진단의 시작점은 애플리케이션 로그가 아니라 최근 커밋이 된다.

### EKS Auto Mode

기본 EKS는 노드 그룹, 오토스케일러, CNI 등을 사용자가 직접 관리해야 한다. **EKS Auto Mode**는 이 인프라 운영 계층을 AWS가 대신 관리하는 모드로, 이번 실습에서는 CloudFormation으로 VPC + EKS Auto Mode 클러스터를 프로비저닝했다. 노드 프로비저닝이 자동으로 처리되어 별도의 노드 관리 작업이 필요 없었다.

### 에이전트 진단 루프 (Tool-Calling)

에이전트는 단일 호출로 결론을 내지 않고, 아래 순서로 도구를 호출하며 정보를 좁혀간다.

| 턴 | 도구 | 목적 |
|---|---|---|
| 1 | `get_recent_changes` | 최근 변경 이력 확인 (Git 커밋) |
| 2 | `get_application` | ArgoCD sync/health 상태 확인 |
| 3 | `list_pods` | 문제 pod 식별 |
| 4 | `get_pod_logs` / `get_events` | 실패 원인 확인 |
| 5 | `send_report` | 진단 결과 발송 (승인 필요) |

이 구조는 "에이전틱 워크플로우"의 최소 단위라고 볼 수 있다. 단일 신호로 판단하지 않고, 서로 다른 데이터 소스(Git, ArgoCD, Pod 상태, 로그/이벤트)를 순차적으로 교차 확인해 가설을 좁혀나가는 방식이다.

### Human-in-the-loop 설계

도구는 읽기 전용(read-only)과 쓰기(write) 두 종류로 나뉜다. `get_*` 계열은 에이전트가 자유롭게 호출하지만, 외부에 실질적 영향을 주는 `send_report`나 `rollback_last_change`는 반드시 사람이 명시적으로 승인(`y`)해야 실행된다. 에이전트의 자율성과 실행 안전성 사이의 경계를 어디에 둘 것인가에 대한 구체적인 구현 예시다.

## 장애 시나리오 3종 비교

세 시나리오 모두 동일한 메커니즘을 공유한다 — `manifests/deployment.yaml`을 Git에 커밋하면 ArgoCD가 클러스터에 반영하고 pod가 실제로 실패한다. 차이는 **무엇을 바꾸는가**와 **어느 데이터 소스에서만 원인이 드러나는가**다.

| 시나리오 | 변경 내용 | 증상 | 원인이 드러나는 위치 |
|---|---|---|---|
| **oom** | memory limit 128Mi → 4Mi | `CrashLoopBackOff`, `OOMKilled` (exit 137) | 현재 로그는 비어있음 — `get_pod_logs(previous=true)`로 직전 컨테이너 로그를 조회해야 확인 가능 |
| **image-tag** | 커밋 메시지 `1.29.0`, 실제 태그 `1.290` (오타) | `ImagePullBackOff` | 로그 자체가 없음(컨테이너 미기동) — `get_events`의 `manifest unknown` 메시지로만 확인 가능 |
| **probe** | readiness 경로 `/` → `/healthz` (nginx에 미존재) | pod는 `Running`, 재시작 없음, 앱 로그 정상 | `get_events`의 `HTTP probe failed: statuscode 404`가 유일한 단서 |

공통 교육 포인트는 **"로그가 비어있다"에서 진단을 멈추지 않는 것**이다. 재시작이 반복 중이면 이전 컨테이너 로그를, 컨테이너가 기동조차 못 했으면 이벤트를, 커밋 메시지와 실제 배포 상태가 다를 수 있다는 전제 하에 Git과 클러스터를 교차 확인해야 한다. 이 원칙이 에이전트 시스템 프롬프트에 명시적으로 반영되어야 하는 이유이기도 하다.

## 시나리오별 진단 과정

### oom: 리소스 limit 미스매치

`status.py` 기준선은 `sync=Synced`, `health=Healthy`, pod 2개 모두 `Running / ready=True / restarts=0`이다. `break_it.py oom` 실행 후 상태는 다음과 같이 바뀐다.

```
Pods
  kdt-dev-api-xxxxx   Running   ready=False   restarts=3   CrashLoopBackOff
                      (직전 종료: OOMKilled exit=137)
최근 이벤트
!  BackOff   Pod/kdt-dev-api-xxxxx   Back-off restarting failed container
```

`solution/agent.py`의 진단 흐름:

1. `get_recent_changes` — 메모리 limit 하향 커밋을 식별
2. `get_application` — ArgoCD `Degraded` 확인
3. `list_pods` — `last_terminated_reason: OOMKilled`, `exit_code: 137` 확인
4. `get_pod_logs` — 현재 로그가 비어있음을 확인하고 `previous=true`로 재조회, 직전 컨테이너 로그 확보
5. `send_report` — 원인(메모리 limit 부족), 근거(커밋 해시 + exit code), 권장 조치(limit 원복)를 정리해 승인 요청

리포트 승인 후 실제 메일로 진단 결과가 도착했고, 실행 종료 시 이번 진단에 사용된 토큰 사용량이 함께 출력됐다. 에이전트가 제안한 `rollback_last_change`를 승인한 뒤 `break_it.py healthy`로 최종 복구, `status.py`로 기준선 상태 복귀를 확인했다.

### 자동 감지: 폴링 기반 트리거

터미널 1에서 `watch.py --agent --solution`을 실행해두고 터미널 2에서 `break_it.py image-tag`로 장애를 주입하면, `watch.py`가 15초 주기로 ArgoCD 상태를 폴링하다 `Degraded`를 감지한 시점에 사람의 개입 없이 진단 루프가 자동으로 시작된다. 실무 환경에서는 이 폴링 자리에 Alertmanager, ArgoCD Notifications, EventBridge 등이 들어가며, "신호 감지 → 루프 시작"이라는 구조 자체는 동일하게 유지된다.

### image-tag: 커밋 메시지와 실제 상태의 불일치

커밋 메시지는 `release: kdt-dev-api 1.29.0 배포`이지만 실제 이미지 태그는 `1.290`이다. Pod는 `Pending`을 거쳐 `ImagePullBackOff`로 전이된다. 컨테이너가 시작되지 않아 로그 자체가 존재하지 않고, 에이전트는 `get_events`에서 `Failed to pull image ... manifest unknown`을 확인한 뒤 커밋 메시지(`1.29.0`)와 실제 태그(`1.290`)의 불일치를 리포트에 명시했다. 세 시나리오 중 가장 대표적인 사례로 꼽히는 이유는, Git 커밋 로그가 "의도"를 나타낼 뿐 "실제 배포된 사실"과 항상 일치하지는 않는다는 점을 가장 직접적으로 보여주기 때문이다.

### probe: 로그로는 포착 불가능한 장애

readiness probe 경로가 `/`에서 `/healthz`로 변경되지만 nginx에는 해당 경로가 없다. Pod는 `Running` 상태를 유지하고 재시작도 없으며 애플리케이션 로그도 정상이다. `list_pods`와 `get_pod_logs`만으로는 이상 신호를 확인할 수 없고, `get_events`의 `Readiness probe failed: HTTP probe failed with statuscode: 404`가 유일한 단서다. 세 시나리오 중 난이도가 가장 높은 이유는 로그 기반 진단 습관으로는 원인에 도달할 수 없는 구조이기 때문이다.

### 클러스터 직접 조회

`kube.py pods -A`, `kube.py events`, `kube.py app`으로 kubectl 설치 없이 클러스터 상태를 조회할 수 있다. `argocd_password.py`로 admin 비밀번호를 발급받아 ArgoCD UI에도 접속했는데, 자체 서명 인증서로 인한 브라우저 경고를 제외하면 실제 운영 환경의 ArgoCD 대시보드와 동일한 UI/UX를 제공한다.

## 환경 구성 과정의 실무적 이슈

교안대로 진행해도 실제 환경에서는 몇 가지 문제가 발생했고, 원인 분석 과정 자체가 이 실습의 진단 원칙(단일 신호로 판단하지 않고 교차 확인)과 동일한 패턴을 따랐다.

**venv 손상**: 기존 `.venv`가 다른 사용자 계정의 Python 경로를 참조하고 있어 `pip install`이 실패했다. venv를 삭제하고 로컬 Python 3.12로 재생성하여 해결했다. venv 디렉터리를 그대로 복사/공유할 경우 자주 발생하는 문제다.

**AWS 자격증명 불일치**: `.env`에 SSO assumed-role의 임시 자격증명(AccessKeyId/SecretAccessKey)을 입력했으나 `InvalidClientTokenId` 오류가 발생했다. 원인은 실습 스크립트가 `AWS_SESSION_TOKEN`을 지원하지 않는다는 점 — 즉 세션 토큰이 필요 없는 **영구 IAM 액세스 키**를 전제로 설계되어 있었다. `EXTRA_ADMIN_ARN`은 별도 용도(콘솔/CloudShell의 kubectl 접근 권한 부여)이며 이 문제와는 무관했다. 해결책은 `infra/create_student_user.py`로 최소 권한 정책(`kdt-lab-student`)이 붙은 실습 전용 IAM 사용자를 생성하고 영구 액세스 키를 새로 발급받는 것이었다.

**콘솔 인코딩**: Windows PowerShell의 기본 코드페이지(cp949)가 스크립트 출력의 이모지(✅/❌)를 렌더링하지 못해 `UnicodeEncodeError`가 발생했다. `$env:PYTHONUTF8="1"`을 세션에 설정하여 해결했다.

## 정리 (Cleanup)

시나리오 검증을 마친 뒤 `cleanup.py`를 실행했다. 삭제 대상을 먼저 출력하고 확인을 받는 방식으로, EKS 클러스터·ArgoCD·Gitea·관련 IAM 리소스가 정리되는 것을 확인했다. 액세스 키 자체는 `.env`에 남아있어 필요 시 `deploy_lab.py` 재실행만으로 동일 환경을 다시 구성할 수 있다.

> EKS 클러스터는 가동 상태를 유지하는 것만으로 하루 약 $5의 비용이 발생한다. 실습 종료 시 `cleanup.py` 실행은 선택이 아니라 필수 단계다.

## 정리하며

이 실습이 보여주는 핵심 메시지는 두 가지로 요약된다.

**1. 단일 데이터 소스로는 진단이 완결되지 않는다.** oom은 exit code라는 비교적 명확한 신호를 남기지만, probe는 pod 상태·재시작 횟수·애플리케이션 로그가 전부 정상으로 보이는 상태에서 이벤트 로그만이 유일한 단서다. 에이전트의 진단 정확도는 결국 얼마나 다양한 소스를 교차 확인하도록 설계됐는지에 좌우된다.

**2. Human-in-the-loop은 형식적 게이트가 아니라 검증 지점이다.** image-tag 시나리오처럼 커밋 메시지(의도)와 실제 배포 상태(사실)가 어긋나는 경우, 에이전트가 생성한 리포트를 사람이 다시 검토하는 과정은 자동화 파이프라인에 반드시 필요한 안전장치로 기능한다.

부수적으로, 실습 환경 구성 단계에서 겪은 문제들(자격증명 종류, 인코딩, venv 관리)을 해결하는 과정 자체도 이 실습이 가르치는 "표면적 증상에서 멈추지 않고 근본 원인까지 좁혀가는" 진단 패턴과 본질적으로 동일했다.
