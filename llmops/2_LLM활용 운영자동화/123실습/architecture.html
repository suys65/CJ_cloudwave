01 요청 하나가 처리되는 전체 흐름

자연어 요청이 들어와 화면에 판정이 찍히기까지의 경로입니다.

"실행 중인 EC2 인스턴스를 확인해줘"

▼

02 파일 계층 구조

아래층일수록 기초, 위층일수록 실제 실습. import는 아래 → 위 한 방향으로만 흐른다.

01~06_*.py실습 스크립트 — 아래 세 모듈을 조합해 진짜 하고 싶은 일에만 집중
▲ import
bedrock_utils.pyBedrock 호출 공통 함수 — converse() · extract_text() · strip_json_fence()
▲ import
aws_clients.pyAWS 연결 — Boto3 Session에서 sts · ec2 · bedrock-runtime 클라이언트 생성
▲ import
config.py설정의 단일 출처 — .env에서 프로파일·리전·모델ID를 읽고 검증(없으면 즉시 중단)

공통 로직을 아래층에 모아두어 순환 의존이 없고, 실습 스크립트는 가벼워진다.

03 Converse API 호출의 구조

지시문을 역할·규칙(system)과 이번 요청(user)으로 나누는 것이 핵심 원리다.

system
"너는 AWS 운영 요청 분석기다. JSON만 반환, 허용값은 이것뿐…" — 매 요청 공통 규칙
messages · user
"실행 중인 EC2 확인해줘" — 이번에 처리할 요청
inferenceConfig
temperature 0.1 (일관성) · maxTokens (응답 길이 상한)
→
response.output.message.content
텍스트 블록 리스트 → extract_text()가 이어붙임
response.usage
inputTokens · outputTokens · totalTokens
response.stopReason
end_turn(정상) · max_tokens(길이 초과로 잘림)

모델은 system을 상위 지침으로 취급 → 규칙을 여기 두면 매번 반복하지 않아도 일관되게 지킨다.

04 조회 / 변경 안전 게이트

LLM에게 판단은 맡기되 실행 권한은 주지 않는다. 이 분기가 실습의 안전 원칙 그 자체다.

operation_type 분류
모델이 요청을 5가지 허용값 중 하나로 판정
▼
read_only 이면 ↙↘ 그 외(change 등)
읽기 전용 명령 생성
command에 aws CLI 문자열
approval_required = false
실행 대상에서 제외
command = null
approval_required = true
▼
화면 출력 → 운영자 검토 → 수동 실행 결정
생성된 명령을 프로그램이 자동 실행하지 않는다
read_only — 조회, 자동 생성 가능 change / security_change — 승인 필요 destructive — 파괴적, 차단

05 06번의 "추측 금지" 패턴

다른 실습과 흐름이 반대다. 먼저 사실을 조회하고, 그 사실만 근거로 요약하게 한다.

① Boto3로 실제 EC2 조회

07 실제 환경에서 조정한 것

교재대로 안 되던 지점들 — 왜 설정을 분리하고 코드에서 방어하는지 여기서 드러난다.

① student 프로파일 없음 — 유효한 자격증명이 admin(SSO)뿐이라 .env의 AWS_PROFILE만 바꿔 해결. 설정을 분리해둔 덕에 코드는 그대로.

② 교재 모델이 Legacy — 지정 모델이 구버전으로 막혀서 활성 모델 global.anthropic.claude-sonnet-4-5로 교체. 모델 ID를 코드에 박지 않은 게 도움.

③ JSON 파싱 실패 — 모델이 답을 ```json … ```로 감싸 json.loads()가 실패. 코드블록을 벗기는 strip_json_fence()를 추가해 03~05에 적용.

④ operation_type이 read가 아니라 read_only여야 — 05 프롬프트에 허용값 목록이 빠져 모델이 read로 답함. 허용값을 명시하니 판정이 정확해짐.
