# 6장. 구조화 출력과 Pydantic 기반 응답 검증

> LLM이 뱉은 JSON을 그대로 믿지 않고, 프로그램이 안전하게 쓸 수 있는 "검증된 데이터"로 만드는 방법을 다룬다. Amazon Bedrock Converse API + Pydantic으로 JSON 기초부터 재시도가 포함된 검증 파이프라인까지 13개 실습을 진행했다.

---

## 이 장을 한 줄로

LLM은 "JSON으로 답해"라고 해도 가끔 규칙을 어긴다(필드 누락, 허용 안 된 값, 타입 오류, 구조 불일치). 이런 결과가 그대로 다음 단계로 넘어가면 시스템이 꼬인다. 그래서 응답과 후속 처리 사이에 **문지기(Pydantic 검증)** 를 세우고, **통과한 데이터만** 저장·자동화에 사용한다.

```
LLM JSON 응답 → Pydantic 검증(규칙 위반이면 차단) → 통과분만 저장·후속처리
```

---

## 왜 구조화 출력과 검증이 필요한가

자연어 출력은 사람이 읽기엔 좋지만, 프로그램이 값을 뽑기엔 불안정하다. "심각도는 높다 / High severity / 긴급 확인 필요"는 뜻은 같아도 문자열이 다 다르다.

그래서 출력을 미리 정한 필드·타입에 맞춘 **JSON**으로 받는다. 하지만 한 가지 함정이 있다.

> `json.loads()`는 **문법만** 검사한다. 아래 JSON은 문법적으로 정상이지만 업무적으로는 전부 틀렸다.
>
> ```json
> { "severity": "매우 위험", "service": 100, "approval_required": "아니오" }
> ```

`severity`가 허용값인가, `service`가 문자열인가, 원인이 3개 이하인가 같은 **업무 규칙**은 문법 검사로 못 잡는다. 이걸 잡는 게 Pydantic이다.

---

## 관련 개념

### 구조화 출력 (Structured Output)
모델 결과를 미리 정의한 필드와 타입에 맞춰 반환하는 방식. 필드 이름으로 값을 조회할 수 있어 조건 분기·저장·API 연동에 바로 연결된다.

### JSON 문법 검증 vs 스키마 검증
- `json.loads()` : 중괄호·따옴표·쉼표 등 **문법**만 확인.
- Pydantic : 필수 필드, 타입, 허용값, 길이, 배열 개수, 중첩 구조, 추가 필드까지 **업무 규칙** 확인.

### Pydantic 핵심 도구

| 도구 | 역할 |
| --- | --- |
| `BaseModel` | 스키마(모델) 정의의 기본 클래스 |
| `ConfigDict(extra="forbid", strict=True)` | 정의 안 된 필드 거부 + 타입 자동변환 금지 |
| `Literal[...]` | 허용값 제한 (예: severity는 low/medium/high/critical/unknown만) |
| `Field(min_length=, max_length=, ge=, le=)` | 문자열·배열 길이, 숫자 범위 제한 |
| 중첩 모델 | 원인·점검항목처럼 여러 필드를 가진 객체를 표현 |
| `field_validator` | 필드별 커스텀 규칙 (예: 조회 명령의 risk_level은 read_only여야) |
| `model_validate_json()` | JSON 문자열을 바로 모델로 검증 |
| `ValidationError.errors()` | 실패한 위치·이유를 구조화해 제공 |

### 검증 실패 시 재시도
검증 오류를 다시 모델에 전달해 "고쳐서 다시 줘"라고 재요청한다. 단 무한 반복은 금지 — `MAX_RETRIES`로 상한을 두고, 초과하면 운영자 검토로 넘긴다.

### JSON vs Markdown
프로그램 내부 처리는 JSON, 사람이 읽는 최종 보고서는 Markdown으로 변환한다.

## 공통 구조

| 파일 | 역할 |
| --- | --- |
| `bedrock_common.py` | Converse 호출(`converse_text`), 응답 텍스트 추출, 토큰 출력 |
| `json_tools.py` | 코드블록 제거 + `{ ... }` 구간 추출(`extract_json_object`) |
| `structured_models.py` | Pydantic 모델 정의 — `IncidentAnalysis`, `Cause`, `RecommendedCheck`, `KubernetesIncident`, `NetworkIncident` |

핵심은 `structured_models.py`다. 여기에 "우리가 허용하는 출력의 모양"을 코드로 못박아 둔다. 예를 들어 `RecommendedCheck`에는 `field_validator`로 "조회 명령의 risk_level은 read_only, approval_required는 false" 정책까지 넣었다. 즉 안전 규칙이 스키마 레벨에서 강제된다.

## 각 실습의 의미와 구현 원리

| # | 실습 | Bedrock | 의미 |
| --- | --- | --- | --- |
| 01 | JSON 파싱 오류 확인 | ✕ | 작은따옴표·마지막쉼표·설명문·코드블록이 왜 파싱 실패하는지 확인 |
| 02 | Bedrock JSON 응답 파싱 | ✓ | 실제 응답에서 JSON을 추출해 `json.loads()` |
| 03 | 기본 Pydantic 검증 | ✕ | 타입 오류·추가 필드를 거부하는지 확인 |
| 04 | Literal·Field 제한 | ✕ | 허용값(urgent 거부)·길이·개수(원인 4개 거부) 제한 |
| 05 | 중첩 모델 검증 | ✕ | 원인·점검항목을 객체 속성으로 접근 |
| 06 | Bedrock→Pydantic 검증 | ✓ | 실제 응답을 `model_validate_json()`으로 검증 |
| 07 | ValidationError 분석 | ✕ | 오류 위치·유형·입력값을 하나씩 읽는 법 |
| 08 | 검증 오류 기반 재시도 | ✓ | 실패 시 오류를 넣어 재호출, 한도 초과 시 운영자 검토 |
| 09 | JSON·CSV 저장 | ✓ | 검증 통과 객체만 파일로 저장 |
| 10 | Kubernetes 검증 | ✓ | 다른 도메인 스키마(status 허용값, 변경/승인 필드) |
| 11 | 네트워크 검증 | ✓ | 포트 범위(1~65535), 점검 계층 검증 |
| 12 | 검증객체→Markdown | ✕ | 검증된 객체를 사람이 읽는 보고서로 변환 |
| 13 | 종합 파이프라인 | ✓ | 호출→검증→재시도→저장 전체 연결 |

03~05, 07은 Bedrock을 부르지 않는다. **일부러 틀린 데이터를 넣어 "잘 거르는지"** 를 보는 실습이다. 06·10·11은 실제 응답을 검증한다. 08·13은 실패 시 재시도, 09·13은 통과분 저장을 담당한다.

## 실행결과를 읽는 법

이 장에서 헷갈리기 쉬운 지점이 하나 있다. **"검증 실패"가 떠도 그게 정상인 실습이 있다.** 실습마다 확인하려는 게 다르기 때문이다.

### ① "잘 거르는지" 보는 실습 (03·04·07) → 검증 실패가 곧 성공
잘못된 데이터를 넣고 문지기가 막는지 본다. 07번 출력을 예로 읽는 법은 이렇다.

```
위치: ('recommended_checks', 0, 'risk_level')
메시지: Value error, risk_level은 read_only여야 합니다.
```

- **위치** = 어느 필드가 틀렸나 → recommended_checks 리스트 0번째 항목의 risk_level
- **메시지** = 왜 틀렸나 → read_only여야 하는데 아니다

이 "위치"를 읽는 게 실전 기술이다. 실제로 모델이 틀린 답을 줬을 때, **어느 필드를 고치라고 프롬프트를 수정할지** 이걸 보고 판단한다.

### ② "통과하는지" 보는 실습 (06·10·11) → 검증 성공이 정상
실제 응답이 스키마를 통과하면 `[검증 성공]`이 뜬다. 규칙을 다 지킨 JSON을 모델이 줬다는 뜻.

### ③ 재시도 실습 (08) → 두 결과 다 정상
```
[1차 호출] → [검증 성공]                     (한 번에 통과)
```
또는
```
[1~3차 호출] → [검증 실패] → 재시도 한도 초과, 운영자 검토 필요
```
무한 반복하지 않고, 몇 번 시도하다 사람에게 넘기는 것까지가 포인트다.

### ④ 저장 실습 (09·13) → results 폴더 확인
```
results/final_analysis.json    ← 검증된 전체 결과
results/final_summary.csv      ← 요약(severity, service, summary, approval_required)
```
모델 원본이 아니라 **검증 통과본만** 저장된다는 게 핵심이다.

## 최종 작동 원리와 구조

13번 종합 파이프라인이 이 장의 결론이다.

```
운영 로그 입력
      │
      ▼
Bedrock Converse 호출  ── converse_text()
      │
      ▼
코드블록 제거 + JSON 추출  ── extract_json_object()
      │
      ▼
Pydantic 검증  ── IncidentAnalysis.model_validate_json()
      │
      ├─ 실패 → 오류를 프롬프트에 넣어 재호출 (최대 MAX_RETRIES)
      │           └─ 한도 초과 → 예외 발생 / 운영자 검토
      │
      ▼ 성공
검증된 객체
      │
      ├─ JSON 저장 (전체 결과)
      └─ CSV 저장 (요약)
```

관통하는 원칙은 하나다. **모델의 원본 응답은 신뢰하지 않는다. 검증을 통과한 객체만 후속 처리에 사용한다.** 프롬프트로 형식을 유도하되, 최종 안전성은 코드(Pydantic)가 보장한다. 이는 앞선 장들과 같은 철학이다 — LLM을 활용하되, 실행/저장 직전에 반드시 코드가 다시 검사한다.

---

## 실행하며 확인한 것

**08·09번 프롬프트 보강** — 원본 프롬프트는 필드 이름만 나열하고 `possible_causes`·`recommended_checks`의 **객체 구조를 보여주지 않았다.** 그 결과 모델이 원인을 문자열로, 점검 항목을 `command` 대신 `description`으로 내놓아 Pydantic(strict) 검증에 전부 실패했다. 특히 **09번은 try/except가 없어 그대로 크래시**했다. 06·13번이 통과한 이유가 프롬프트에 **정확한 JSON 구조 예시**가 있었기 때문이며, 같은 구조 블록을 08·09에 넣으니 검증 통과·저장까지 정상 동작했다.

> 이 사건 자체가 6장의 교훈이다. "프롬프트로 JSON을 요청해도 검증은 반드시 필요하다"는 명제를, 09번이 검증 없이 돌다 크래시하며 몸소 보여줬다.

**모델 특성** — 선택한 모델이 한글로 길게 답하는 편이라, JSON이 큰 출력은 토큰 여유가 필요하다(5장과 동일 교훈). 6장은 프롬프트에 명시적 구조를 준 덕에 출력이 정돈되어 대부분 문제없이 통과했다.

## 정리

- 자연어 출력은 읽기 쉽지만 자동 처리엔 불안정하다. JSON으로 받아 필드·타입을 일정하게 유지한다.
- `json.loads()`는 문법만, Pydantic은 업무 규칙(필수·타입·허용값·길이·중첩·추가필드)까지 검증한다.
- `Literal`로 허용값, `Field`로 길이·범위, 중첩 모델로 복합 구조, `field_validator`로 안전 정책을 스키마에 못박는다.
- `model_validate_json()`으로 응답을 바로 검증하고, `ValidationError.errors()`로 실패 위치를 정확히 읽는다.
- 검증 실패 시 오류를 넣어 제한적으로 재시도하고, 한도를 초과하면 운영자에게 넘긴다.
- 검증을 통과한 결과만 저장·자동화에 사용한다. 내부는 JSON, 사용자 출력은 Markdown으로 변환한다.

```
Converse 호출 → JSON 추출 → Pydantic 검증
→ (실패 시 재시도) → 통과분만 저장 → 필요 시 Markdown 보고서
```
