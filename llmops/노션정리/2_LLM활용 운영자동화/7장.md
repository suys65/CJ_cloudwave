# 7장. 토큰·컨텍스트·비용·성능 최적화

> LLM 호출은 한 번은 싸도 반복되면 비용이 쌓인다. 이 장은 **무엇을 측정하고, 어떻게 줄이고, 어떤 모델을 고를지**를 실제 숫자로 확인한다. Bedrock Converse의 `usage`(토큰)와 응답시간을 측정해, 전처리·maxTokens·모델 크기가 비용에 미치는 영향을 비교한다.

---

## 이 장을 한 줄로

목표는 "비용을 최소화"가 아니라 **정확도·응답시간·비용·안전성의 균형**을 찾는 것이다. 그러려면 먼저 측정해야 한다 — 입력 토큰, 출력 토큰, 응답시간, 모델별 단가.

---

## 왜 비용 최적화인가

한 번의 호출이 저렴해도 환경에 따라 전체 비용은 빠르게 커진다.
```
인원 20명 × 1인당 하루 50회 × 4일 = 4,000회 호출
```
게다가 **가장 싼 모델이 항상 최선은 아니다.** 소형 모델이 오분류를 반복하면 재호출·운영자 검토·잘못된 티켓 라우팅 같은 숨은 비용이 붙는다. 반대로 모든 작업에 대형 모델을 쓰면 낭비다. 그래서 "측정 → 비교 → 적절한 모델 배치"가 이 장의 흐름이다.

---

## 관련 개념

### 입력 토큰 / 출력 토큰
- **입력 토큰**: 모델에 전달되는 모든 것 — System Prompt, User Prompt, Few-shot 예시, 로그, 스키마 설명, 이전 대화까지 전부.
- **출력 토큰**: 모델이 생성한 응답 전체.

### 총비용 계산식
```
총비용 = 입력토큰 × 입력단가 + 출력토큰 × 출력단가
       = (입력토큰 / 1,000,000 × 입력단가) + (출력토큰 / 1,000,000 × 출력단가)
```
출력 단가가 입력 단가보다 비싼 모델이 많아, **출력 길이 제한이 특히 중요**하다.

### usage
Converse 응답의 `usage`에 `inputTokens / outputTokens / totalTokens`가 담긴다. 모델·응답 유형에 따라 없을 수 있어 `get()`으로 안전하게 읽는다.

### 응답시간
`time.perf_counter()`로 호출 전후를 잰다. 이 값에는 로컬 처리·네트워크·Bedrock 처리·모델 추론·응답 반환이 모두 포함되므로 **순수 추론 시간은 아니다.** 여러 번 재서 평균을 보는 게 맞다.

### maxTokens
최대 출력 길이 제한. 비용·응답시간을 줄이지만, 너무 작으면 JSON이 잘리거나 항목이 누락된다.

### 소형 / 대형 모델
- **소형**: 분류·필드 추출·짧은 요약·대량 반복에 적합. 싸고 빠름.
- **대형**: 복합 장애 분석·여러 소스 종합·긴 보고서에 적합. 비싸고 느림.

### 모델 라우팅
모든 요청을 한 모델에 보내지 않고, **작업 난이도에 따라 소형/대형을 골라 보내는** 전략. 품질을 유지하면서 전체 비용을 줄이는 핵심.

## 공통 모듈

| 파일 | 역할 |
| --- | --- |
| `usage_utils.py` | 응답에서 토큰 사용량·응답시간 추출(`extract_usage`) |
| `measured_converse.py` | Bedrock 호출 + 측정을 한 함수로(`converse_with_usage`) |
| `response_utils.py` | 응답의 모든 text 블록 결합(`extract_text`) |
| `cost_utils.py` | 토큰·단가로 예상 비용 계산(`calculate_cost`) |
| `bedrock_client.py` | (보충) Bedrock Runtime 클라이언트 생성 |

핵심은 `converse_with_usage()`다. 호출 직전 `perf_counter()`로 시작 시각을 찍고, `client.converse()` 후 경과 시간을 계산해 `extract_usage()`로 토큰과 함께 반환한다. 덕분에 모든 실습이 **호출과 측정을 한 줄로** 처리한다.

---

## 각 실습의 의미와 구현 원리

### 01 · 로그 전처리 (Bedrock 호출 없음)
`Counter`로 중복 로그를 개수로 집계하고(`ERROR database timeout ×3`), `startswith`로 WARN 이상만 필터링한다. "긴 로그를 모델에 다 보내지 말고, 줄여서 보낸다"는 개념을 코드로 보여준다.

### 02 · 전처리 전후 토큰 비교
같은 로그를 **원본**과 **전처리본**으로 각각 호출해 입력 토큰을 비교한다. 모델·프롬프트·출력 설정은 동일하게 두고 입력만 바꾼다. 감소율은 `(원본-전처리)/원본×100`으로 계산한다. → 이 장에서 가장 중요한 실습.

### 03 · maxTokens 비교
같은 프롬프트를 `maxTokens` 200·500·1000으로 호출해 출력 토큰·응답시간·**`stopReason`** 을 비교한다. `stopReason`이 `max_tokens`면 답이 잘린 것, `end_turn`이면 끝까지 답한 것.

### 04 · 소형 vs 대형 모델
같은 장애 데이터를 소형·대형 모델에 각각 보내 토큰·응답시간을 비교한다. 토큰·속도만으로 고르지 않고, 응답 내용(품질)을 별도 채점표(요약 정확성·사실/가설 구분·근거 연결 등)로 함께 평가한다.

### 05 · 통합 리포트
02·03·04가 만든 CSV 세 개를 `pandas.concat`으로 합쳐 `usage_report.csv` 하나로 만든다. 예시 숫자가 아니라 **실제 호출에서 측정한 값**이 모인다.

## 실측 결과

| 실습 | 결과 |
| --- | --- |
| 02 전처리 효과 | 입력 토큰 **288 → 147, 48.96% 감소** |
| 03 maxTokens | 200·500 → `max_tokens`(잘림) / 1000 → `end_turn`(완료) |
| 04 소형 vs 대형 | nova ≈ 4초 vs sonnet ≈ 15초 (품질은 대형이 우위) |
| cost_utils | 입력 2000·출력 500 토큰 → 약 $0.0135 |

전처리로 입력이 절반으로 줄고, 대형 모델은 품질을 얻는 대신 응답시간이 3배 이상 든다는 게 숫자로 드러났다.

---

## 실행 결과를 읽는 법

측정 실습이라, 화면·CSV에서 **어느 값을 보는지**가 중요하다.

| 볼 지표 | 의미 |
| --- | --- |
| `input_tokens` (02) | 전처리로 입력이 얼마나 줄었나 → 감소율 |
| `stop_reason` (03) | `max_tokens`=잘림 / `end_turn`=정상 완료 |
| `elapsed_seconds` (04) | 소형 vs 대형 응답시간 차이 |
| `output` 컬럼 (CSV) | 모델별 응답 품질을 직접 비교 |

**주의:** 토큰이 줄었다고 무조건 성공이 아니다. 장애 원인 판단에 필요한 정보가 유지됐는지 함께 봐야 한다. 최적화는 항상 **품질과 같이** 평가한다.

## 최적화 전략 (종합)

이 장이 제시하는 비용 절감 수단들:

1. **입력 줄이기** — 시간 범위 제한, 로그 레벨 필터(WARN↑), 중복 집계, 핵심 필드만 추출, 입력 구조화([환경]/[메트릭]/[핵심 로그]).
2. **프롬프트 압축** — 중복 지시 제거, 출력 항목 수 제한, 공통 규칙은 System Prompt로 재사용.
3. **출력 제한** — 업무별 `maxTokens` 조정(분류는 짧게, 보고서는 길게).
4. **모델 라우팅** — 단순 작업은 소형, 복합 분석은 대형, 이미지는 VLM.
5. **재시도 제한** — `MAX_RETRIES`로 상한(재시도 1회면 비용 ≈ 2C). 오류 원인을 수정 프롬프트에 담아서만 재시도.
6. **동시성·배치** — 다수 동시 호출 시 호출량·출력 길이 통제, 형식이 동일한 짧은 항목은 배치로 묶기.

## 정리

- LLM 비용은 **입력 토큰 · 출력 토큰 · 호출 횟수 · 모델 단가**로 결정된다.
- Converse의 `usage`와 `perf_counter()`로 토큰·응답시간을 측정한다.
- 긴 로그는 시간 범위·레벨 필터·중복 집계·핵심 필드로 줄이고, 프롬프트는 중복 지시를 없앤다.
- `maxTokens`는 비용을 줄이지만 너무 작으면 응답이 잘린다(`stop_reason`으로 확인).
- 단순 작업은 소형, 복합 분석은 대형 — **모델 라우팅**이 품질을 지키며 비용을 줄이는 핵심.
- 재시도는 상한을 두고, 최적화는 항상 **비용과 품질을 함께** 비교한다.

```
측정(usage·시간) → 입력·출력·프롬프트 최적화 → 모델 라우팅 → 재시도 제한 → 결과 비교(비용+품질)
```
