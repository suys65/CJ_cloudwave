# LLM으로 운영 메시지를 분류하고 심각도에 따라 작업을 분기하기

운영 알림을 LLM으로 분석해 `category`·`severity`·`summary`로 구조화하고, 심각도에 따라 서로 다른 후속 작업(Downstream Task)으로 분기하는 실습을 정리한다. Amazon Bedrock Converse API와 Boto3를 사용한다.

---

## 왜 이 실습을 하는가

운영 환경에서는 서버, 애플리케이션, 보안 시스템에서 다양한 메시지가 끊임없이 발생한다.

```
웹 서버 CPU 사용률이 95%입니다.
10분 동안 로그인 실패가 30회 발생했습니다.
애플리케이션 배포가 정상적으로 완료되었습니다.
```

사람은 이 문장을 읽고 "성능 문제인지 보안 문제인지, 얼마나 급한지, 무엇을 해야 하는지"를 판단한다. 문제는 이런 판단을 사람이 일일이 하기에는 알림이 너무 많다는 점이다. 규모가 커지면 하루 수천 건이 쏟아지고, 그 사이에서 정작 중요한 장애 알림이 묻힌다.

이 실습의 목표는 그 판단 단계를 자동화하는 것이다. 다만 LLM에게 모든 것을 맡기지 않고, **판단은 LLM이, 검증과 실행은 프로그램이** 나눠 맡는 구조를 만든다. 이것이 실무 운영 자동화(AIOps)의 최소 단위다.

이번 실습에서는 후속 작업을 Slack 알림이나 장애 티켓 대신 **파일 저장**으로 단순화한다. AWS 비용이나 추가 권한 없이 전체 흐름만 안전하게 연습하기 위해서다.

## 핵심 개념

### 비정형 텍스트를 구조화 데이터로 변환

프로그램은 자연어 문장을 그대로 처리하지 못한다. `if` 조건으로 분기하려면 정해진 형태의 데이터가 필요하다.

```
"웹 서버 CPU 사용률이 95%입니다"     ← 프로그램이 분기할 수 없는 형태
        │  LLM 분류
        ▼
{ "category": "performance", "severity": "high", "summary": "..." }
                                                 ← severity 필드로 분기 가능
```

LLM의 역할은 이 변환이다. 애매한 문장에서 유형과 심각도를 뽑아, 코드가 소비할 수 있는 JSON으로 바꾼다.

### category — 문제의 종류

| category | 의미 | 예 |
| --- | --- | --- |
| `performance` | 성능·자원 사용량 | CPU, 메모리, 디스크, 응답 지연 |
| `security` | 보안 | 로그인 실패, 권한 거부 |
| `availability` | 가용성 | 서버 중단, 연결 실패, HTTP 500 반복 |
| `normal` | 정상 상태·완료 | 배포 완료, 백업 성공 |

### severity — 문제의 심각도

| severity | 의미 | 후속 작업 |
| --- | --- | --- |
| `low` | 정상·낮은 위험 | 정상 기록 |
| `medium` | 주의 필요 | 경고 기록 |
| `high` | 즉시 확인 필요 | 장애 기록 |

`category`는 문제의 종류를, `severity`는 심각도를 나타낸다. 두 축은 독립적이다. 같은 `performance`라도 디스크 72%는 `medium`, 98%는 `high`가 된다.

### Downstream Task — 앞 단계 결과로 수행하는 후속 작업

분류 결과를 받아 다음 작업을 수행한다. 이 실습에서는 심각도별로 저장 파일을 나눈다.

```
severity = low     → output/normal.jsonl
severity = medium  → output/warning.jsonl
severity = high    → output/incident.jsonl
```

파일에 저장하는 이 작업이 Downstream Task다.

## 처리 흐름

```
운영 메시지 입력
      │
      ▼
Bedrock Converse API 호출
      │
      ▼
LLM이 category · severity · summary 생성 (JSON)
      │
      ▼
JSON 문자열 추출 → 파싱
      │
      ▼
필드·허용값 검증
      │
      ▼
severity 값으로 작업 분기
      ├─ low    → output/normal.jsonl
      ├─ medium → output/warning.jsonl
      └─ high   → output/incident.jsonl
```

전체 코드는 `app.py` 하나에 담는다. 구성은 다음과 같다.

| 구성 | 함수 | 역할 |
| --- | --- | --- |
| 분류 | `classify_message()` | Bedrock 호출 → 응답 텍스트 확보 |
| 추출 | `extract_json()` | 텍스트에서 JSON 객체 파싱 |
| 검증 | `validate_result()` | 필수 필드·허용값 확인 |
| 분기 | `route_task()` | severity로 저장 파일 결정 |
| 실행 | `save_result()` | JSON Lines로 파일에 추가 |

## 동작 원리

### 출력 형식을 JSON으로 강제한다

LLM에게 "이 메시지를 분석해줘"라고만 하면 응답 형식이 매번 달라진다. 사람이 읽기에는 괜찮지만 프로그램이 `severity` 값을 정확히 추출하기 어렵다. 그래서 system 프롬프트에서 출력 형식과 규칙을 못 박는다.

```
반드시 다음 JSON 형식으로 출력한다.
{ "category": "...", "severity": "...", "summary": "..." }

- JSON 이외의 설명을 출력하지 않는다.
- 마크다운 코드 블록을 사용하지 않는다.
- 입력에서 확인되지 않는 내용을 추측하지 않는다.
```

분류 기준도 프롬프트에 명시한다. 예를 들어 "사용률 90% 이상은 high, 70~90%는 medium" 같은 임계값을 규칙으로 준다. 기준이 구체적일수록 결과가 일관된다.

### temperature를 0으로 둔다

`temperature`는 응답의 무작위성을 조절한다. 분류 작업은 매번 같은 입력에 같은 결과가 나와야 하므로 `0.0`으로 설정한다. 다만 temperature가 낮아도 출력이 항상 완전히 동일하다고 보장할 수는 없다. 그래서 검증 단계가 반드시 필요하다.

### 판단은 LLM, 검증과 실행은 프로그램

이 실습에서 가장 중요한 설계다. 역할을 명확히 나눈다.

| 구분 | 역할 |
| --- | --- |
| LLM | 비정형 메시지를 이해하고 category·severity·summary로 분류 |
| 프로그램 | LLM 출력이 허용값인지 검증 |
| 프로그램 | severity에 따라 정해진 규칙으로 작업 선택 |
| 프로그램 | 선택된 작업을 실제로 실행 |

LLM은 가끔 허용하지 않은 값을 반환한다. 예를 들어 이런 응답이 올 수 있다.

```json
{ "category": "cpu_problem", "severity": "very_high", "summary": "CPU 문제" }
```

`cpu_problem`과 `very_high`는 정의한 허용값이 아니다. `validate_result()`는 이런 값을 걸러 예외를 발생시킨다.

```python
if category not in ALLOWED_CATEGORIES:
    raise ValueError(f"허용되지 않은 category 값임: {category}")
```

분기 기준도 LLM이 쓴 자유로운 요약 문장이 아니라 구조화된 `severity` 필드를 사용한다.

```python
# 사용하지 않는 방식 — 요약 표현은 모델마다 달라짐
if "심각" in result["summary"]:
    ...

# 사용하는 방식 — 허용값이 정해진 필드로 분기
if result["severity"] == "high":
    ...
```

이 구조 덕분에 LLM이 예상치 못한 응답을 생성해도 프로그램의 실행 범위는 정해진 규칙을 벗어나지 않는다. "LLM을 믿되, 실행 권한은 주지 않는다"는 원칙이다.

### JSON Lines로 저장한다

결과는 한 줄에 JSON 객체 하나를 담는 JSON Lines(`.jsonl`) 형식으로 저장한다.

```python
with output_file.open("a", encoding="utf-8") as file:
    file.write(json.dumps(record, ensure_ascii=False))
    file.write("\n")
```

`"a"`(append) 모드라 파일 전체를 다시 쓰지 않고 실행할 때마다 한 줄씩 덧붙인다. 로그처럼 누적되는 데이터에 적합하다.

## 실행 결과

여섯 개의 테스트 메시지를 입력한 결과는 다음과 같다.

| 운영 메시지 | category | severity | 저장 파일 |
| --- | --- | --- | --- |
| 백업 작업이 정상적으로 완료되었습니다. | normal | low | normal.jsonl |
| 웹 서버 메모리 사용률이 82%입니다. | performance | medium | warning.jsonl |
| 웹 서버 CPU 사용률이 96%입니다. | performance | high | incident.jsonl |
| 사용자 로그인 실패가 5회 발생했습니다. | security | medium | warning.jsonl |
| 관리자 로그인 실패가 30회 반복되었습니다. | security | high | incident.jsonl |
| 데이터베이스 연결 실패로 서비스가 중단되었습니다. | availability | high | incident.jsonl |

`incident.jsonl`에 저장된 레코드 예시는 다음과 같다.

```json
{"processed_at":"2026-07-28T00:23:47+00:00","input_message":"웹 서버 CPU 사용률이 96%입니다.","analysis":{"category":"performance","severity":"high","summary":"웹 서버 CPU 사용률이 96%로 임계치를 초과했습니다."},"downstream_task":{"task_name":"create_incident","description":"장애 기록 생성"}}
```

입력 메시지, 분석 결과, 선택된 작업, 처리 시각이 함께 기록된다. 나중에 이 파일만 봐도 무엇이 어떻게 처리됐는지 추적할 수 있다.

## 트러블슈팅

### 모델 ID 변수명 불일치

실습 예제 코드에는 변수명 오류가 있었다. 환경변수는 `BEDROCK_MODEL_ID_1`로 읽어 `BEDROCK_MODEL_ID` 변수에 담는데, 함수 안에서는 정의되지 않은 `BEDROCK_MODEL_ID_1`을 참조했다. 이 상태로 실행하면 `NameError`가 발생한다.

```python
# 오류: 정의되지 않은 이름 참조
if not BEDROCK_MODEL_ID_1:
modelId=BEDROCK_MODEL_ID_1

# 수정: 실제로 정의된 변수 사용
if not BEDROCK_MODEL_ID:
modelId=BEDROCK_MODEL_ID
```

환경변수 이름(`BEDROCK_MODEL_ID_1`)은 그대로 두고, 파이썬 변수 참조만 `BEDROCK_MODEL_ID`로 통일해 해결했다.

### 모델 선택

활성 상태인 모델을 사용해야 한다. 구버전(Legacy)으로 표시된 모델은 호출이 거부되므로, `.env`의 `BEDROCK_MODEL_ID_1`에 현재 사용 가능한 모델 ID를 지정한다.

### JSON 파싱 실패

LLM이 JSON을 코드블록으로 감싸거나 설명을 덧붙이면 파싱이 실패할 수 있다. `extract_json()`은 먼저 전체를 파싱해 보고, 실패하면 정규식으로 `{ ... }` 구간만 찾아 다시 파싱한다. 프롬프트로 "JSON만 출력"을 지시하되, 코드에서도 방어 처리를 둔 것이다.

## 확장 — 저장 대상만 바꾸면 실전이 된다

이 실습은 후속 작업을 파일 저장으로 구현했다. 하지만 앞단(입력 → 분류 → 검증 → 분기)은 그대로 두고 마지막 단계만 교체하면 실무로 확장된다.

```
normal   → Amazon S3 아카이브
warning  → Amazon SNS 알림
incident → Slack 장애 알림 또는 Jira 티켓 자동 생성
```

중요한 것은 저장 대상이 바뀌어도 전체 처리 구조는 달라지지 않는다는 점이다.

```
LLM 분석 → 검증 → 작업 분기 → Downstream Task
```

## 정리

이번 실습에서 확인한 내용은 두 가지다.

첫째, LLM은 비정형 운영 메시지를 코드가 처리할 수 있는 구조화 데이터로 바꾼다. 이 변환이 있어야 자동 분기와 라우팅이 가능하다.

둘째, LLM에 판단은 맡기되 실행은 맡기지 않는 설계가 안전한 자동화의 핵심이다. LLM의 출력을 허용값으로 검증하고, 정해진 규칙(`severity` 필드)으로만 분기하고, 실제 실행은 프로그램이 담당한다. 이렇게 하면 LLM이 예상치 못한 응답을 내놓아도 시스템은 정해진 범위 안에서만 동작한다.

파일 저장이라는 단순한 후속 작업으로 연습했지만, 이 구조 자체가 운영 알림을 자동 분류하고 심각도별로 대응하는 실무 자동화의 기본 골격이다.
