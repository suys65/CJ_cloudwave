# 5장. 고급 프롬프트 설계와 운영 장애 분석

> LLM을 "긴 답을 잘 쓰는 도구"가 아니라 "정해진 기준을 안정적으로 따르고, 그 결과를 프로그램이 검증할 수 있게 내놓는 부품"으로 다루는 방법을 정리한다. Amazon Bedrock Converse API와 Boto3로 Zero-shot부터 종합 장애 분석 티켓 생성까지 10개 실습을 진행했다.

---

## 이 장을 한 줄로

단순 프롬프트로는 운영 데이터를 다루기 어렵다. **사실과 추론을 구분하고, 근거를 붙이고, 안전 규칙을 지키고, JSON으로 검증 가능한 출력**을 만들려면 프롬프트를 구체적으로 설계해야 한다.

---

## 왜 고급 프롬프트가 필요한가

`장애 원인을 분석해줘` 같은 요청은 범위가 없다. 모델은 확인된 사실, 장애 유형, 심각도, 가능한 원인, 근거, 확인 절차, 승인 필요 작업 중 무엇을 만들어야 하는지 알 수 없다. 그래서 아무렇게나 자연스러운 문장을 쓴다.

운영 데이터에 단순 프롬프트를 쓰면 네 가지 문제가 반복된다.

| 문제 | 내용 | 예 |
| --- | --- | --- |
| 원인 단정 | 근거 없이 원인을 확정 | "신규 코드의 메모리 누수가 원인이다" (메모리 지표는 입력에 없음) |
| 사실·가설 혼합 | 확인된 것과 추측을 섞음 | "무한 루프로 CPU가 증가했다" (CPU 증가는 사실, 무한 루프는 가설) |
| 필드 누락 | 한 번에 많은 걸 시키면 일부 빠짐 | summary만 있고 verification이 없음 |
| 안전 미준수 | 조회/변경을 구분 못함 | `kubectl rollout undo`를 실행 명령으로 제안 |

고급 프롬프트는 모델의 역할뿐 아니라 **출력 순서, 허용값, 근거 작성 방식, 불확실성 표현, 금지 작업**까지 지정해 이 문제를 줄인다. 그리고 프롬프트만으로는 부족하므로, 응답을 받은 뒤 **코드에서 다시 검증**한다.

## 관련 개념

### 프롬프트 엔지니어링 vs Downstream Task

- **Downstream Task**: 모델이 수행할 업무 목적·입력·출력·제약·평가 기준을 정의한 것.
- **프롬프트 설계**: 그 Task를 실제 모델 호출에 적용해 원하는 형식과 품질의 결과를 얻는 과정.

```
Task 정의 → 프롬프트 작성 → 모델 호출 → 응답 파싱 → 출력 검증 → 프롬프트 개선
```

### Zero-shot과 Few-shot

- **Zero-shot**: 예시 없이 작업 설명과 분류 기준만 준다. 짧고 빠르지만, 조직 고유 기준을 반영하기 어렵고 출력이 흔들릴 수 있다.
- **Few-shot**: 입력–출력 예시를 함께 준다. 예시는 답의 모양뿐 아니라 **조직의 분류 체계, 유사 category의 경계, 정보 부족 시 처리(unknown), 출력 형식**을 전달한다. 교육 실습에서는 3~6개의 명확한 예시로 시작하고, 실패 사례를 보며 경계 예시를 추가한다.

### 경계 사례와 unknown

비슷해 보이지만 분류가 다른 입력을 경계 사례라 한다.

```
Connection refused to database host   → network
Database authentication failed        → authentication
OutOfMemoryError                      → resource
NullPointerException                  → application
```

정보가 부족한 입력(`ERROR operation failed`)은 `unknown`으로 처리한다. unknown을 허용하지 않으면 모델이 근거 없이 아무 category나 고른다.

### 사실과 추론, 그리고 근거

- **확인된 사실(facts)**: 입력에서 직접 확인되는 것. ("10:05 CPU가 94%로 증가했다")
- **가능한 원인(possible_causes)**: 사실을 근거로 만든 가설. 확정하지 않는다.

가설에는 근거를 붙인다.

| 근거 유형(evidence_type) | 의미 |
| --- | --- |
| `direct` | 로그·설정에 직접 명시된 사실 |
| `temporal` | 이벤트 발생 순서 |
| `correlation` | 여러 지표가 함께 변한 관계 |
| `configuration` | 설정 값과 증상의 관계 |
| `general_knowledge` | 일반적인 기술 패턴 |

신뢰 수준(confidence)은 `high / medium / low`로 표시한다. **시간 순서만으로 인과관계를 확정하면 안 된다.** "배포 후 CPU가 올랐다"는 시간적 연관성일 뿐, "배포가 CPU 증가의 직접 원인"이라고 쓰려면 추가 근거가 필요하다.

### 안전 정책 — 조회 vs 변경

- **조회 작업**: 진단용 정보 수집 (`systemctl status`, `kubectl logs`). 실행해도 안전.
- **변경 작업**: 서비스 상태에 영향 (`restart`, `rollout undo`, `reboot`). 분석 결과만으로 실행하면 안 된다.

출력에서 둘을 분리한다. 조회는 `recommended_checks`에, 변경은 `proposed_actions`에 **설명만** 쓰고 `command: null`, `approval_required: true`로 둔다.

### Self-check와 다중 호출

- **Self-check**: 모델이 만든 초안을 다시 검토하도록 별도 호출을 보낸다. 근거 없는 단정, 필드 누락 등을 잡는다. 다만 **코드 기반 검증을 대체하지 않는다.**
- **다중 호출**: 복합 작업을 여러 호출로 쪼갠다(사실 추출 → 분류 → 티켓). 중간 결과를 코드로 검증하고 실패한 단계만 재시도할 수 있다. 대신 호출 수·비용·지연이 늘어난다.

### 평가

예시 하나가 잘 됐다고 프롬프트가 좋은 건 아니다. 대표·경계·정보부족 사례를 포함한 테스트 데이터로 정확도를 측정한다.

```
정확도 = 정답과 일치한 개수 / 전체 테스트 개수
```

정확도 외에 허용값 위반, unknown 처리, 특정 category 편향, 반복 일관성도 함께 본다.

## 공통 구조 (bedrock_common.py)

모든 실습이 공유하는 헬퍼 모듈이다. Converse 호출과 후처리를 한곳에 모아 각 실습을 가볍게 유지한다.

| 함수 | 역할 |
| --- | --- |
| `get_model_id()` | `.env`에서 모델 ID를 읽고 검증 |
| `create_bedrock_runtime()` | 프로파일 기반 Bedrock Runtime 클라이언트 생성 |
| `invoke_text()` | Converse 호출 → 응답 텍스트 + 사용량(usage/stopReason) 반환 |
| `extract_text()` | 응답의 텍스트 블록 결합 |
| `parse_json_object()` | 응답에서 `{ ... }` 구간을 찾아 JSON 파싱 |
| `normalize_label()` | 단일 라벨 출력 정리(공백·코드블록·따옴표 제거, 소문자화) |
| `print_metadata()` | 토큰 사용량·지연시간 출력 |

핵심은 `invoke_text()`가 system(역할·규칙)과 user(이번 요청)를 나눠 보내고, `parse_json_object()`가 모델이 JSON 앞뒤에 군더더기를 붙여도 파싱을 시도한다는 점이다.

## 각 실습의 의미와 구현 원리

### 01 · Zero-shot 로그 분류
예시 없이 category 하나만 출력하게 한다. `OutOfMemoryError → resource`가 나오면 성공. 모델의 일반 기준과 수업 기준이 다르면 결과가 어긋날 수 있다는 걸 확인하는 출발점이다.

### 02 · Zero-shot vs Few-shot
같은 로그를 두 방식으로 호출해 비교한다. Few-shot이 예시로 준 기준을 적용하는지 본다. **이번 환경에서는 Few-shot이 `OutOfMemoryError`를 `resource`가 아닌 `application`으로 분류**했다 — 예시에 메모리 경계 사례가 없으면 모델이 "자바 예외 = application"으로 볼 수 있다. 예시를 보강해야 한다는 걸 직접 보여주는 사례다.

### 03 · 경계 사례와 unknown
system 프롬프트에 분류 기준을 명시하고 5개 경계 사례를 채점한다. DB 연결 거부(network)와 DB 인증 실패(authentication), OOM(resource)과 NPE(application)를 구분하는지, 정보 부족은 unknown으로 두는지 확인한다. → 정확도 5/5.

### 04 · 단계별 장애 분석
한 번의 호출 안에서 출력 순서를 지정한다(facts → timeline → category → possible_causes → additional_information → summary). 코드로 필수 필드 누락과 원인 3개 이하를 검증한다. **한 호출로 복합 분석을 받되, 구조를 코드가 확인**하는 방식.

### 05 · 근거 기반 JSON
각 원인에 `evidence_type`, `evidence`, `confidence`, `verification`을 붙이게 한다. 코드가 evidence_type·confidence를 허용값과 대조하고 verification 존재를 확인한다. **"그럴듯한 설명"과 "근거 있는 가설"을 구분**하는 핵심 실습.

### 06 · 안전한 점검 절차
조회는 `recommended_checks`, 변경은 `proposed_actions`로 분리해 출력하게 한다. 코드가 조회 명령에 금지어(`rollout undo`, `systemctl restart`, `rm -` 등)가 없는지, 변경 작업이 `command: null` + `approval_required: true`인지 다시 검사한다. **프롬프트 + 코드 이중 안전장치.**

### 07 · 초안 생성과 Self-check
1차 호출로 초안을 만들고, 2차 호출로 원본과 초안을 비교 검토해 `valid / problems / revised_result`를 받는다. 모델이 스스로 초안을 점검하는 흐름을 경험한다.

### 08 · 다중 호출 파이프라인
사실 추출 → 장애 분류 → 티켓 생성을 **세 번의 호출**로 나눈다. 앞 호출의 JSON 결과를 다음 프롬프트에 넣어 연결한다. 중간 결과를 각각 확인·검증할 수 있는 게 장점.

### 09 · 일괄 평가
테스트 데이터 6건을 실제로 호출해 정답과 비교하고 정확도를 낸다. 오분류 사례를 뽑아 Few-shot 개선 재료로 쓴다. → 정확도 6/6.

### 10 · 종합 장애 분석 (최종 형태)
지금까지의 모든 기법을 하나로 합친다. 하나의 호출로 **운영 티켓 + facts + timeline + 원인(근거·신뢰도·확인방법) + 조회 절차 + 승인 필요 작업 + 추가 정보**를 JSON으로 생성하고, 코드가 원인 개수·승인 규칙을 검증한다.

## 최종 작동 원리와 구조

10번 종합 실습이 이 장의 결론이다. 전체 파이프라인은 다음과 같다.

```
운영 이벤트 + 컨텍스트 입력
        │
        ▼
system 프롬프트(분석 규칙 + 안전 규칙) + user 프롬프트(상황 + 출력 스키마)
        │
        ▼
Bedrock Converse 호출  ── invoke_text()
        │
        ▼
JSON 응답 파싱  ── parse_json_object()
        │
        ▼
코드 검증
  ├─ 원인 후보 3개 이하인가
  ├─ proposed_actions.command 가 null 인가
  └─ proposed_actions.approval_required 가 true 인가
        │
        ▼
구조화된 장애 분석 결과(티켓/근거/조회절차/승인작업)
```

이 구조를 관통하는 원칙은 두 가지다.

**1. 사실과 추론을 분리하고, 추론에는 근거를 요구한다.**
facts와 possible_causes를 다른 필드로 나누고, 원인마다 evidence_type·confidence·verification을 붙인다. 시간 순서만으로 원인을 확정하지 않는다.

**2. 판단은 LLM, 검증과 실행 제한은 코드.**
LLM은 분석과 초안을 만들고, 조회/변경을 나눈다. 하지만 최종 안전성은 코드가 보장한다. 금지어 검사, 허용값 대조, 개수 제한, 승인 필드 확인은 모두 프로그램이 다시 한다. 이래야 모델이 예상치 못한 응답을 내도 시스템은 정해진 범위를 벗어나지 않는다.

이는 앞선 실습들(운영 요청 분석, 운영 메시지 분류)과 같은 철학이다. LLM을 신뢰하되, 실행 권한은 주지 않는다.

## 실행하며 확인한 것

**출력 잘림(truncation)** — 선택한 모델이 한글로 길게 답해서, JSON이 완성되기 전에 `maxTokens`에 걸려 잘렸다(`stop_reason: max_tokens`). 잘린 JSON은 파싱 단계에서 `JSONDecodeError`로 실패한다. JSON이 큰 실습(04·06·10)은 토큰 한도를 넉넉히 올려 해결했다. → 출력 구조가 복잡하고 응답이 길수록 토큰 여유가 필요하다.

**Few-shot 결과의 흔들림** — 02번에서 OOM이 `application`으로 분류됐다. 코드 문제가 아니라 예시 부족이다. 경계 예시를 추가하면 개선된다. 프롬프트 품질은 예시 하나가 아니라 반복 평가로 다듬어야 한다는 걸 보여준다.

## 정리

- 고급 프롬프트 설계의 목표는 긴 답변이 아니라, **Task 기준을 안정적으로 따르고 프로그램이 검증할 수 있는 출력**이다.
- Zero-shot은 빠른 시험, Few-shot은 조직 기준·경계·형식 전달에 쓴다.
- 사실과 가능한 원인은 분리하고, 원인에는 근거·신뢰도·확인방법을 붙인다.
- 조회와 변경은 출력에서 나누고, 변경은 승인 필요로 격리한다.
- Self-check는 보조 수단이며, JSON 파싱·필수 필드·허용값·개수·금지어·승인 필드는 코드가 다시 검사한다.
- 프롬프트 품질은 여러 테스트 데이터로 반복 평가해 개선한다.

```
Task 기준 확인 → Zero/Few-shot 작성 → Converse 호출 → 파싱
→ 사실·근거·안전 검증 → Self-check/다중 호출 → 테스트 평가 → 프롬프트 개선
```
