# 56실습. Bedrock 기반 자연어 SQL 생성과 Streamlit 시각화

> 사용자가 한국어로 "카테고리별 매출 TOP 5 보여줘"라고 물으면, LLM이 Athena SQL을 만들고, 실제로 S3 데이터를 조회해 표와 차트로 보여주는 앱을 구현했다. 이 글은 개념보다 **구현 구조·작동 원리·데이터 흐름**에 초점을 둔다.

---

## 이 실습을 한 줄로

자연어 질문을 **Bedrock이 SQL로 번역** → **코드가 그 SQL을 검증** → **Athena가 S3 데이터를 조회** → **Streamlit이 표·차트로 시각화**하는, 자연어 BI(비즈니스 인텔리전스) 도구를 만든다.

---

## 전체 데이터 흐름

이 실습의 핵심은 데이터가 여러 AWS 서비스를 거쳐 변환되는 흐름이다.

```
사용자 자연어 질문 ("월별 매출 추이 보여줘")
        │
        ▼
Streamlit 입력창                         [화면]
        │
        ▼
Bedrock Converse (nova-lite)             [자연어 → SQL 번역]
        │  프롬프트 = 테이블 스키마 + 규칙 + 질문
        ▼
생성된 SQL 텍스트
        │
        ▼
extract_sql() → validate_sql()           [코드펜스 제거 + 안전 검증]
        │  SELECT만 / 금지어 차단 / 허용 테이블만
        ▼
Athena start_query_execution()           [비동기 쿼리 시작]
        │  상태 폴링 (QUEUED→RUNNING→SUCCEEDED)
        ▼
Athena가 결과 CSV를 S3에 저장            [s3://버킷/athena-results/{쿼리ID}.csv]
        │
        ▼
S3 get_object() → pandas.read_csv()      [CSV → DataFrame]
        │
        ▼
Streamlit 표(st.dataframe) + Plotly 차트  [화면]
```

각 화살표에서 데이터의 형태가 바뀐다: **자연어 문자열 → SQL 문자열 → 쿼리 실행 ID → S3의 CSV 파일 → pandas DataFrame → 웹 화면**. 이 변환의 연쇄가 이 앱의 뼈대다.

## 구현 구조 (파일별 역할)

기능을 4개 파일로 분리했다. "SQL 만들기"와 "쿼리 실행하기"를 나눈 게 핵심이다.

| 파일 | 역할 | 핵심 함수 |
| --- | --- | --- |
| `bedrock_sql_generator.py` | 자연어 → SQL 번역 + 검증 | `generate_sql_from_question()`, `extract_sql()`, `validate_sql()` |
| `athena_utils.py` | Athena 쿼리 실행 → DataFrame 반환 | `run_athena_query()` |
| `03_ask_cli.py` | 터미널 테스트용 | (두 모듈 조합) |
| `04_streamlit_app.py` | 웹 UI + 차트 | Streamlit + Plotly |
| `.env` | 리전·버킷·DB·모델 ID 설정 | — |

이렇게 나누면 CLI(`03`)로 먼저 로직을 검증한 뒤 웹앱(`04`)을 붙일 수 있다. 앱은 두 모듈의 함수를 호출만 한다.

## 작동 원리

### 1. 자연어 → SQL : 스키마를 프롬프트에 주입한다

모델에게 질문만 던지면 컬럼 이름도 매출 계산식도 몰라 엉뚱한 SQL을 만든다. 그래서 **테이블 구조를 프롬프트에 함께 넣는다.**

```
데이터베이스/테이블 이름
컬럼 목록과 의미 (order_date=주문일, region=지역 ...)
매출 계산식: (quantity * unit_price - discount_amount)
규칙: SELECT만, 변경문 금지, LIMIT 100, SQL 외 설명 금지
```

예를 들어 "매출"이라는 단어를 모델이 임의로 `SUM(unit_price)`로 계산하면 틀린다. 계산식을 명시했기 때문에 `SUM(quantity*unit_price-discount_amount)`를 만든다. `temperature=0.0`으로 두어 같은 질문엔 같은 SQL이 나오게 한다.

### 2. SQL 추출 : 코드펜스를 벗긴다

모델이 SQL을 ` ```sql ... ``` ` 코드블록으로 감싸는 경우가 있다. `extract_sql()`이 정규식으로 코드블록 안쪽만 꺼낸다. 없으면 응답 전체를 SQL로 본다.

### 3. SQL 검증 : 실행 전에 코드가 막는다 (가장 중요)

**모델이 만든 SQL을 그대로 실행하면 위험하다.** 사용자가 "테이블 삭제해줘"라고 하거나 모델이 실수로 `DROP TABLE`을 만들 수 있다. 그래서 `validate_sql()`이 실행 직전에 세 가지를 검사한다.

```python
1. SELECT로 시작하지 않으면 → 차단
2. 금지 키워드(insert/update/delete/drop/alter/create/... )가 있으면 → 차단
3. 허용된 테이블(ecommerce_sales)이 SQL에 없으면 → 차단
```

이 검증은 프롬프트의 "SELECT만 만들어라"라는 지시와 **이중 안전장치**다. 프롬프트는 유도일 뿐이고, 최종 차단은 코드가 한다. (실제 테스트에서 DROP·DELETE·information_schema 조회가 전부 차단됐다.)

### 4. Athena 실행 : 비동기 + 결과는 S3에

Athena 쿼리는 **바로 결과를 주지 않는다.** 이 비동기 특성을 이해하는 게 `run_athena_query()`의 핵심이다.

```
start_query_execution()  → 쿼리 실행 ID만 반환 (결과 아님)
        │
반복: get_query_execution()으로 상태 확인
       QUEUED → RUNNING → SUCCEEDED  (1초 간격 폴링)
        │
SUCCEEDED면 결과 CSV가 S3에 저장됨
        │
s3.get_object()로 CSV 문자열을 읽고
StringIO로 감싸 pandas.read_csv() → DataFrame
```

`StringIO`를 쓰는 이유: S3에서 읽은 CSV는 파일이 아니라 **문자열**이라, pandas가 파일처럼 읽게 감싸주는 것이다. 상태 폴링에 `time.sleep(1)`을 두는 이유: 안 두면 API를 너무 빠르게 반복 호출한다.

### 5. Streamlit 시각화 : 컬럼을 축에 자동 매핑

DataFrame이 오면 앱은 **첫 번째 컬럼을 X축, 두 번째 컬럼을 Y축**으로 잡아 차트를 그린다.

```
| category | sales |     →   X축=category, Y축=sales
| 전자기기  | 2.9억 |
```

차트 유형(막대/선/파이)에 따라 Plotly 함수(`px.bar/px.line/px.pie`)를 골라 그린다. 컬럼이 1개면(예: 전체 매출 합계) 차트 대신 표만 보여준다. 전 과정을 `try/except`로 감싸, 오류가 나도 앱이 죽지 않고 화면에 메시지를 띄운다.

## 관통하는 원칙

> **"SQL 생성은 LLM에게, 실행 여부 판단은 코드가."**

- LLM : 자연어를 SQL로 번역 (사람이 하던 일)
- 코드 : 그 SQL이 안전한지(SELECT만, 허용 테이블만) 실행 전에 검증

이는 앞선 실습들과 같은 철학이다. LLM은 실수하거나 악용될 수 있으니, 실제 실행(여기선 DB 쿼리) 직전에 코드가 한 번 더 막는다. 이 앱에서 그 방어선이 `validate_sql()`이다.

## 실제 구축한 인프라와 데이터 흐름 실측

파이프라인이 돌려면 조회 대상 데이터가 있어야 한다. 다음을 구성했다.

| 구성 | 값 |
| --- | --- |
| S3 버킷 | `nlp-s3-analytics-...` (서울 리전) |
| 원천 데이터 | `datasets/.../ecommerce_sales.csv` (500행) |
| Athena DB / 테이블 | `nlp_s3_analytics_db` / `ecommerce_sales` (12컬럼, date·int·boolean 타입) |

Athena 테이블은 S3의 CSV를 **직접 읽는 외부 테이블(EXTERNAL TABLE)** 이다. 데이터를 복사하지 않고 S3 위치만 가리키며, 헤더 줄은 `skip.header.line.count=1`로 건너뛴다. 즉 "S3의 CSV = 테이블"인 구조다.

실측 결과:

```
질문: 카테고리별 매출 TOP 5
→ 전자기기 2.9억 > 가구 1.3억 > 패션 4130만 ...

질문: 지역별 주문 건수
→ 서울 109 > 대구 108 > 부산 100 ...

질문: 반품률 TOP 5
→ 가구 12.3% > 패션 11.2% > 전자기기 10.6% ...
```

자연어 질문이 실제 S3 데이터 조회 결과로 이어지는 전 과정이 동작했다.

## 조정하고 배운 것

**모델 ID** — 문서 기본값 `amazon.nova-lite-v1:0`은 이 리전에서 직접 호출이 안 되고 추론 프로파일이 필요해, `apac.amazon.nova-lite-v1:0`로 바꿨다.

**자격증명** — 원본 코드는 기본 자격증명을 쓰지만, `.env`에 `AWS_PROFILE`을 지정하면 boto3가 자동으로 그 프로파일을 사용한다. 코드 수정 없이 프로파일을 붙일 수 있다.

**정수 나눗셈 함정** — "반품률"을 물었을 때 모델이 `SUM(...)/COUNT(*)`로 정수끼리 나눠 결과가 전부 0이 됐다. 정수 나눗셈은 소수점을 버리기 때문이다. 프롬프트에 "비율 계산 시 100.0을 곱하거나 CAST(... AS double)"라는 규칙 한 줄을 추가하니 정상 퍼센트가 나왔다. → **프롬프트에 계산 규칙을 얼마나 구체적으로 주느냐가 SQL 품질을 좌우한다.**

## 정리와 확장

이 실습은 다음 구조를 구현한 것이다.

```
CSV → S3 → Athena 테이블 → Bedrock 자연어 SQL → Athena 조회 → pandas → Streamlit 시각화
```

핵심은 **자연어와 데이터베이스 사이에 LLM을 번역기로 두되, 실행 전 검증으로 안전을 지킨다**는 것. 같은 구조로 저장 대상(테이블)과 프롬프트만 바꾸면 다음으로 확장된다.

```
운영 로그 자연어 질의 도구
클라우드 비용 분석 챗봇
보안 이벤트 조회 시스템
관리자용 자연어 BI 대시보드
```

앞 장들이 "LLM 출력을 분류·분석·검증"하는 것이었다면, 이 실습은 그 출력을 **실제 데이터 조회로 연결**해 눈에 보이는 결과(표·차트)까지 만든 마무리다.
```
자연어 → (LLM 번역) → SQL → (코드 검증) → Athena → 데이터 → 시각화
```
