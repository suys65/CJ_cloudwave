# 8장_실습. LLM 기반 AWS 운영 챗봇 (캡스톤)

> 지금까지 배운 것(자연어 분류·구조화 출력·검증·비용 최적화·보안 계층)을 하나로 합쳐, 실제 Terraform 인프라를 대상으로 동작하는 운영 챗봇을 만든다. 이 글은 구현 구조뿐 아니라, **실제 인프라를 띄우며 겪은 장애와 해결 과정, 실험 결과**를 중심으로 정리한다.

---

## 이 실습을 한 줄로

자연어로 "현재 서버 상태 알려줘"라고 물으면, **LLM이 질문을 분류 → Boto3가 실제 AWS 데이터를 수집 → LLM이 데이터를 근거로 분석 → Pydantic이 검증**해서 답하는 챗봇이다. 여기에 실제 ALB+ASG+EC2 운영 환경을 Terraform으로 띄우고, 장애를 인위로 발생시켜 챗봇이 제대로 진단하는지 검증한다.

---

## 전체 아키텍처

```
로컬 PC
  Streamlit(채팅 UI) → FastAPI(/api/chat)
        │
        ├─ classify_question()   Bedrock: 질문 → RouteDecision(category)
        ├─ execute_route()       Boto3: EC2/ASG/ALB/CloudWatch/Logs 수집
        └─ analyze_incident()    Bedrock: 데이터 → IncidentAnalysis(JSON) → Pydantic 검증
        │
        ▼ AWS API
Terraform 인프라
  VPC(2 Public Subnet) → ALB → Target Group → ASG(EC2 ×2) → FastAPI 샘플 앱
                                                   │
                                          CloudWatch Agent → Logs
                                          CloudWatch Alarm(CPU/5xx/Unhealthy)
                                          Systems Manager(SSH 없이 접속)
```

데이터 흐름은 앞 장들과 같은 패턴이다: **판단은 LLM, 실행·검증은 코드.** `classify_question`이 질문 유형을 정하지만 실제 AWS 조회는 코드(`execute_route`)가 하고, `analyze_incident`의 결과는 Pydantic(`IncidentAnalysis`)이 다시 검증한다.

## 관련 개념

### 라우팅 (질문 분류)
자연어 질문을 `overall_status / ec2_status / asg_status / alb_status / metric_analysis / log_analysis / incident_analysis / command_generation / report_generation / unsupported` 10개 카테고리로 분류한다. 분류 결과에 따라 **어떤 Boto3 수집기를 호출할지**가 정해진다 — 이게 "도구 선택"의 역할을 한다.

### 수집기(Collectors)와 규칙 기반 요약
`ec2_collector`, `asg_collector`, `alb_collector`, `cloudwatch_collector`, `logs_collector` 다섯 개가 원본 AWS 데이터를 가져온다. `calculate_basic_health()`처럼 **명확히 계산 가능한 것(healthy 개수, 알람 개수)은 Python이 직접 계산**하고, LLM은 그 위에서 의미 해석만 담당한다.

### Fault-tolerant 수집
수집기 하나가 실패해도(예: ASG가 아직 없음) 전체 요청이 죽지 않도록 `_safe()` 래퍼로 감싼다. 이건 교안 §18에 "일부 서비스 실패 시 나머지 결과 유지"로 명시된 개선 과제였다.

### 구조화 분석과 Pydantic
`IncidentAnalysis`는 `severity / summary / evidence / possible_causes / recommended_checks / recommended_actions / requires_human_approval / uncertainty`를 강제한다. 6장에서 다룬 원칙 그대로 — LLM 응답을 바로 쓰지 않고 스키마로 검증한 것만 반환한다.

### 안전한 명령 (Read-only 판별)
`is_read_only_command()`가 `aws ec2 describe-`처럼 허용된 접두사인지 검사한다. 실제 실행은 하지 않고, 승인이 필요한 변경 작업(`command_generation`)은 화면에 초안만 보여준다 — 8장(보안) 원칙의 연장선.

## Terraform 구성과 실제 배포

교안 문서에는 `terraform.tfvars`(변수 값)와 `outputs.tf`만 있고 **`main.tf` 등 리소스 정의 코드는 원래 텍스트에 없었다**(강사가 폴더로 배포하는 전제). tfvars 스펙에 맞춰 새로 작성했다.

```
VPC(10.0.0.0/16) + Public Subnet ×2 + IGW + RouteTable
Security Group(ALB: 80 개방 / Instance: ALB에서만 app_port 허용)
IAM Role(SSM + CloudWatchAgent) + Instance Profile
Launch Template(AL2023, user_data)
ALB + Target Group(health check: /health) + Listener
ASG(min1/desired2/max3) + CPU Target Tracking(70%)
CloudWatch Alarm ×3(High CPU / ALB 5xx / TG Unhealthy)
```

`terraform validate` → *"Success! The configuration is valid."*, `terraform plan` → **23 to add, 0 error**, `terraform apply` → **23개 리소스 생성 완료**.

## 트러블슈팅 — 실제로 겪은 4가지 인프라 문제

**여기가 이 실습의 핵심이다.** 코드가 문법적으로 맞아도 실제 클라우드에 배포하면 예상 못한 문제가 나온다는 걸 그대로 보여준다.

### ① 크래시 루프 — 인스턴스가 계속 교체됨

`dnf update -y`(OS 전체 업데이트)가 부팅을 5분 가까이 지연시켰는데, `health_check_grace_period`가 기본 120초라 ASG가 "부팅 실패"로 오판 → 인스턴스를 계속 종료·재생성하는 크래시 루프가 발생했다.

```
해결: dnf update 제거(필요한 패키지만 설치) + grace_period 600초로 상향
```

### ② SSM 접속 불가 — Session Manager로 못 들어감

`aws ssm start-session`이 `TargetNotConnected`로 실패. 원인은 AMI 필터 `al2023-ami-*-x86_64`가 **minimal 변형**(`al2023-ami-minimal-...`)을 매칭했기 때문. minimal 이미지는 SSM Agent가 기본 설치되어 있지 않다(표준 AL2023엔 있음).

```
해결: 필터를 al2023-ami-2023.*-kernel-*-x86_64로 좁혀 표준 이미지만 매칭
     + user_data에 amazon-ssm-agent 명시적 설치·활성화(이중 안전장치)
```

### ③ desired_capacity 반복 드리프트 — 2대가 자꾸 1대로 줄어듦

`terraform apply`로 desired=2를 맞춰도 몇 분 뒤 다시 1로 떨어지는 현상이 3번 반복됐다. 원인은 버그가 아니라 **CPU Target Tracking 정책의 정상 동작**이었다 — 인스턴스가 유휴 상태(CPU ≈0%)라 "목표 70%에 맞추려면 인스턴스가 덜 필요하다"고 판단해 자동으로 축소(scale-in)시킨 것.

```
Cause 로그: "a monitor alarm ...AlarmLow... triggered policy
             ...cpu-target-tracking changing desired capacity from 2 to 1"

해결: target_tracking_configuration에 disable_scale_in = true 추가
     (scale-out은 유지, scale-in만 비활성화)
검증: 5분간 desired=2로 안정 유지 확인
```

### ④ `metric_analysis`/`alb_status` 라우팅 미연결

"최근 15분 CPU와 오토스케일링 상태를 분석해줘"라고 물으면 **"지원하지 않는 질문 유형입니다"** 가 나왔다. 원인은 교안 §18에 이미 "개선 과제"로 명시돼 있던 부분 — `execute_route()`가 `ec2_status`·`asg_status`·`log_analysis`·`overall_status`·`incident_analysis`만 처리하고 `metric_analysis`·`alb_status`는 연결이 안 돼 있었다(수집기 함수 `get_ec2_cpu`, `get_target_health` 등은 이미 만들어져 있었는데 라우터가 안 부름).

```
해결: execute_route()에 metric_analysis(CPU 시계열+ASG+알람),
     alb_status(로드밸런서+타겟그룹+타겟헬스) 분기 추가
검증: 실제 CPU 부하 상태에서 재질문 → "CPU 100% 포화 상태" 정확히 진단
```

## 장애 실험과 결과

### 실험 A — CPU 부하 (§22)
```bash
aws ssm start-session --target <instance-id> --profile admin --region ap-northeast-2
for i in 1 2; do yes > /dev/null & done   # CPU 100%
```
**결과**: 챗봇이 `metric_analysis` 카테고리로 정확히 분류하고, 실시간 CloudWatch CPU 데이터를 근거로 **"CPU 100% 포화 상태 발생"** 을 정확히 진단했다. (수정 ④ 검증과 겸함)

### 실험 B — 서비스 중지 (§23)
```bash
sudo systemctl stop llmops-app
```
**결과**: Target이 `unhealthy`(`Target.FailedHealthChecks`)로 정확히 전환됐다. 그런데 예상 못한 지점이 있었다 — **ASG의 `health_check_type=ELB` 설정 때문에, unhealthy 인스턴스를 ASG가 스스로 감지해 자동 교체(self-healing)** 시켰다. 새 인스턴스가 뜨고 기존 것은 draining 되는 동안 ALB는 계속 `200 OK`를 유지했다.

> 버그가 아니라 오히려 아키텍처의 자가치유 능력을 보여준 사례다. 다만 "unhealthy 상태"를 챗봇으로 여유 있게 관찰하려면 시간이 짧다 — 관찰 시간을 늘리려면 일시적으로 자동복구를 꺼야 한다:
> ```bash
> aws autoscaling suspend-processes --auto-scaling-group-name kyt-llmops-asg \
>   --scaling-processes HealthCheck ReplaceUnhealthy
> # 실험 후
> aws autoscaling resume-processes --auto-scaling-group-name kyt-llmops-asg
> ```

### 실험 C — HTTP 500 폭탄 (§24, 방법만 준비됨)
```bash
python scripts/generate_error_requests.py http://<ALB_DNS>
```
`/error` 엔드포인트를 반복 호출해 ALB 5xx 지표와 애플리케이션 로그를 동시에 발생시키는 스크립트다. 핵심 교훈은 **Target Health가 `healthy`여도 특정 기능은 실패할 수 있다**는 것 — Health Check(`/health`)는 앱 전체 기능을 보장하지 않는다.

## 관통하는 원칙

이번에도 결론은 같다: **LLM은 판단하고, 코드는 검증·통제한다.**

- 질문 분류는 LLM, 실제 AWS 조회는 Boto3 코드
- 장애 원인 추론은 LLM, 결과 형식은 Pydantic이 강제
- 조치 명령은 LLM이 제안, 실행 여부·안전성은 `is_read_only_command()`와 사람 승인이 결정
- 인프라 문제(크래시 루프·SSM·오토스케일링 드리프트)는 **AWS 서비스의 실제 동작 방식을 이해해야만** 원인을 찾을 수 있었다 — LLM이 아무리 잘 분석해도, 밑단 인프라가 튼튼해야 그 분석이 의미가 있다.

## 정리

이 캡스톤은 지금까지의 장들을 한 시스템으로 묶는다.

```
자연어 질문 분류 (4장·5장)
    +
구조화 출력과 검증 (6장)
    +
비용을 고려한 수집 범위 설계 (7장)
    +
안전한 명령·승인 흐름 (8장 보안)
    =
실제 AWS 인프라를 관찰·진단하는 운영 챗봇
```

그리고 실제로 인프라를 띄워보며 얻은 가장 큰 교훈은 따로 있다 — **`terraform apply`가 성공했다고 끝이 아니다.** AMI 변형, 헬스체크 유예시간, 오토스케일링 정책의 부작용처럼, 실제로 돌려봐야만 드러나는 문제들이 있었고, 그걸 하나씩 로그와 지표로 근거를 찾아 고치는 과정 자체가 이 실습의 핵심 경험이었다.
