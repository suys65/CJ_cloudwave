# LLM 기반 AWS 운영 요청 분석과 조회 명령 생성

Amazon Bedrock과 Boto3를 사용해 자연어 운영 요청을 분석하고, 안전한 읽기 전용 명령을 생성하는 실습을 정리한다. 개념, 아키텍처, 코드 동작 원리, 그리고 실제 환경에서 조정한 부분을 다룬다.

---

## 배경

운영 업무에서는 AWS CLI 명령을 매번 정확히 기억하기 어렵다. "실행 중인 EC2 목록을 보는 명령이 무엇인지"를 자연어로 물으면 알맞은 조회 명령을 만들어주는 도구가 있으면 유용하다.

이번 실습의 목표는 다음과 같다.

- 자연어 운영 요청을 LLM으로 분석해 대상 서비스와 작업 유형을 분류한다.
- 조회(읽기) 작업만 CLI 명령으로 생성한다.
- 재부팅, 삭제, 보안 그룹 변경 같은 변경 작업은 명령을 생성하지 않고 승인 필요 상태로 표시한다.

즉 LLM에 실행 권한을 주는 것이 아니라, 판단과 초안 작성까지만 맡기고 실행 여부는 운영자가 결정하는 구조다.

---

## 개념 정리

### LLM (Large Language Model)

대량의 텍스트로 학습해 다음에 올 토큰을 예측하도록 훈련된 모델이다. 입력 문장에 이어질 내용을 확률적으로 생성하며, 별도 규칙 없이 요약·분류·번역·코드 생성 등 다양한 작업을 처리한다.

### Foundation Model

특정 작업 하나에 특화되지 않고 여러 작업에 범용으로 사용하도록 학습된 대형 모델이다. 이번 실습에서 사용한 Claude가 여기에 해당한다. 프롬프트만 바꾸면 로그 분석기, 요청 분류기, 명령 생성기 등으로 역할이 바뀐다.

### Amazon Bedrock

여러 제공사의 파운데이션 모델을 AWS에서 API로 호출해 사용하는 관리형 서비스다. 모델을 직접 배포·운영할 필요 없이 AWS 자격증명만으로 추론 요청을 보낼 수 있다. 클라이언트는 두 가지로 구분된다.

- `bedrock` : 모델 목록 조회, 설정 관리 등 관리용
- `bedrock-runtime` : 실제 추론 요청을 보내는 실행용

이 실습에서는 추론이 목적이므로 `bedrock-runtime`을 사용한다.

### Converse API

Bedrock에서 모델과 상호작용하는 표준 호출 방식이다. 요청을 `system`(역할·규칙), `messages`(대화 내용), `inferenceConfig`(추론 옵션)로 구조화한다. 모델별 요청 형식 차이를 추상화해, 모델을 교체해도 코드를 거의 그대로 유지할 수 있다.

### 프롬프트 엔지니어링

원하는 출력을 얻기 위해 지시문을 설계하는 작업이다. "JSON만 반환", "허용값은 정해진 목록뿐", "부가 설명 금지" 같은 제약을 프롬프트에 명시해, 모델이 프로그램에서 바로 소비 가능한 형태로 응답하도록 유도한다.

### 운영 자동화

인프라·서버 운영 작업을 사람이 수동으로 처리하지 않고 자동화·반자동화하는 것을 말한다. LLM을 결합하면 자연어 요청을 해석해 적절한 작업을 식별하는 단계까지 자동화할 수 있다. 다만 위험한 작업은 승인 절차를 거치게 하는 안전장치가 필요하다.

## 처리 흐름

요청 하나가 처리되는 경로는 다음과 같다.

```
자연어 요청 (예: "실행 중인 EC2 확인해줘")
   │
   ▼
converse() 로 Amazon Bedrock 호출
   │   system 프롬프트 = 역할·규칙 (고정)
   │   user  프롬프트 = 이번 요청 (매 호출 변경)
   ▼
모델 응답 (JSON 형태 텍스트)
   │
   ▼
텍스트 추출 → 코드블록 제거 → json.loads()
   │
   ▼
service / operation_type / command 판정 → 출력
```

로컬 파이썬은 요청을 구성해 전송하고 응답을 정리하는 역할을 맡고, 실제 분석은 Bedrock 모델이 수행한다.

## 프로젝트 구조

파일은 역할별 4개 계층으로 나뉜다. import는 아래 계층에서 위 계층으로 한 방향으로만 흐르며 순환 의존이 없다.

```
config.py         ← .env에서 설정값 로드
   ▲
aws_clients.py    ← Boto3 세션 및 AWS 클라이언트 생성
   ▲
bedrock_utils.py  ← Bedrock 호출 공통 함수
   ▲
01~06_*.py        ← 위 세 모듈을 조합한 실습 스크립트
```

공통 로직(설정, 연결, 호출)을 하위 계층에 모으면 실습 스크립트는 핵심 로직에만 집중할 수 있다.

### config.py

```python
load_dotenv()  # .env 내용을 환경변수로 로드

AWS_PROFILE = os.getenv("AWS_PROFILE", "")
BEDROCK_MODEL_ID = os.getenv("BEDROCK_MODEL_ID", "")

if not BEDROCK_MODEL_ID:
    raise ValueError("BEDROCK_MODEL_ID가 설정되지 않았다.")
```

계정 정보와 모델 ID를 코드가 아닌 `.env`에 두고, `.gitignore`로 `.env`를 저장소에서 제외한다. 모델 ID가 비어 있으면 모듈 로드 시점에 예외를 던져 실행을 중단한다. 잘못된 설정으로 동작하는 것보다 조기에 실패하는 편이 안전하다.

### aws_clients.py

```python
session = boto3.Session(profile_name=AWS_PROFILE, region_name=AWS_REGION)

sts_client      = session.client("sts")             # 인증 주체 확인
ec2_client      = session.client("ec2")             # EC2 조회
bedrock_runtime = session.client("bedrock-runtime") # 모델 호출
```

`Session`은 AWS CLI에 등록된 프로파일을 재사용하므로 코드에 액세스 키를 넣지 않는다. 세 클라이언트는 모듈 로드 시 한 번만 생성해 재사용한다.

### bedrock_utils.py

핵심 함수 세 개로 구성된다.

**converse() — 모델 호출**

```python
bedrock_runtime.converse(
    modelId=BEDROCK_MODEL_ID,
    system=[{"text": system_prompt}],                       # 역할·규칙
    messages=[{"role": "user",
               "content": [{"text": user_prompt}]}],        # 이번 요청
    inferenceConfig={"temperature": 0.1, "maxTokens": 800}, # 추론 옵션
)
```

**extract_text() — 응답에서 텍스트 추출**

Converse 응답의 `content`는 블록 리스트다. 이 중 텍스트 블록만 골라 연결한다.

```python
content_blocks = response["output"]["message"]["content"]
texts = [b["text"] for b in content_blocks if "text" in b]
return "\n".join(texts)
```

**strip_json_fence() — 코드블록 제거**

모델이 JSON을 마크다운 코드블록(` ```json … ``` `)으로 감싸는 경우 `json.loads()`가 실패한다. 파싱 전에 앞뒤 코드블록 표시를 제거해 순수 JSON만 남긴다. 자세한 내용은 아래 트러블슈팅에서 다룬다.

## 동작 원리

### system과 user 프롬프트 분리

Converse API는 지시문을 두 영역으로 나눈다.

- `system` : 모든 요청에 공통 적용되는 역할과 규칙 (예: "AWS 운영 요청 분석기이며, JSON만 반환한다")
- `user` : 이번에 처리할 실제 요청

모델은 `system`을 상위 지침으로 취급한다. 규칙을 여기에 정의하면 매 요청마다 규칙을 반복하지 않아도 일관되게 적용된다.

### temperature를 낮게 두는 이유

`temperature`는 응답의 무작위성을 조절한다. 값이 높으면 다양성이 커지지만 매번 결과가 달라지고, 낮으면 같은 입력에 대해 거의 동일한 결과가 나온다. 분류와 명령 생성은 일관성이 중요하므로 `0.1`로 낮게 설정한다.

### JSON 출력 유도

03~05번 실습에서는 모델이 자유 서술 대신 정해진 스키마의 JSON으로 응답하도록 제약한다.

```
허용 service:        [ec2, cloudwatch, logs, autoscaling, elbv2, unknown]
허용 operation_type: [read_only, change, security_change, destructive, unsupported]

규칙:
- JSON 객체 하나만 반환한다.
- 설명을 덧붙이지 않는다.
- 조회 작업은 read_only로 분류한다.
...
출력 형식:
{ "service": "", "operation_type": "", "approval_required": false, ... }
```

허용값과 출력 형식을 사전에 지정하면 응답을 `json.loads()`로 바로 파싱해 처리할 수 있다. 사람이 읽는 문장이 아니라 프로그램이 소비하는 데이터로 받는 것이다.

## 실습 구성

| 실습 | 내용 | 목적 |
| --- | --- | --- |
| 01 | STS로 현재 인증 주체 확인 | 프로파일·자격증명 연결 검증 |
| 02 | nginx 로그를 전달해 진단 명령 요청 | Converse 기본 호출, 토큰 사용량·종료 이유 확인 |
| 03 | 요청을 service·operation_type으로 분류 | 자연어 → 구조화된 JSON |
| 04 | 요청을 위험도(read_only~prohibited)로 분류 | 위험도 기준 분류 |
| 05 | 조회 요청 → 읽기 전용 CLI 명령 생성 | 조회/변경 구분, 명령 초안 |
| 06 | 실제 EC2 조회 → LLM 요약 | 실데이터 기반 요약 |

03~05번은 동일한 패턴을 공유한다. system에 규칙을 정의하고, 요청 목록을 반복 호출하며, 응답 JSON을 파싱해 출력한다. 프롬프트만 교체하면 같은 모델이 분류기가 되기도 하고 명령 생성기가 되기도 한다.

## 06번: 실데이터 기반 요약

06번은 다른 실습과 흐름이 반대다.

```
① Boto3로 실제 EC2 상태 조회 (사실 수집)
② 조회 결과를 프롬프트에 주입
③ "제공된 결과만 근거로 요약"하도록 요청
```

LLM은 현재 AWS 계정의 실시간 상태를 알지 못한다. 상태를 그냥 물으면 근거 없이 생성(환각)할 수 있다. 이를 막기 위해 실제 조회 결과를 컨텍스트로 제공하고, system 프롬프트에서 다음과 같이 제한한다.

```
- 제공된 EC2 조회 결과만 사용한다.
- 입력에 없는 상태를 생성하지 않는다.
- 인스턴스가 없으면 없다고 작성한다.
```

이는 검색으로 확보한 사실을 근거로 답하게 하는 RAG의 기초 형태다. 또한 조회 결과 전체가 아니라 필요한 7개 필드만 추려 전달한다. 토큰 비용을 줄이고 민감정보 전달을 최소화하기 위해서다.

이번 실습 환경에는 EC2 인스턴스가 없어 06번은 빈 목록(`[]`)을 받았고, 모델은 규칙대로 "인스턴스가 없습니다"라고 응답했다.

## 안전 설계

핵심 원칙은 LLM에 판단은 맡기되 실행 권한은 부여하지 않는 것이다.

1. **명령 자동 실행 금지** — 05번은 생성한 명령을 출력만 한다. 실제 실행은 운영자가 검토 후 직접 수행한다.
2. **조회/변경 분리** — 변경·보안변경·파괴적 작업은 `command`를 `null`로 두고 `approval_required`를 `true`로 설정해 실행 대상에서 제외한다.
3. **최소 권한** — 실습 프로파일에는 가능한 한 조회 권한만 부여한다.
4. **민감정보 제거** — 액세스 키, 비밀번호 등은 모델에 전달하기 전에 제거한다.

## 트러블슈팅

교재 기준으로 진행하는 과정에서 실제 환경과 달라 조정한 부분이다.

### student 프로파일 부재

교재는 `student` 프로파일을 전제하지만, 실제로는 유효한 자격증명이 `admin`(SSO)뿐이었다. `.env`의 `AWS_PROFILE` 값만 변경해 해결했다. 자격증명을 코드가 아닌 설정으로 분리했기 때문에 코드 수정은 필요 없었다.

### 모델 ID가 Legacy로 표시됨

교재의 모델 ID로 호출하자 다음 오류가 발생했다.

```
This Model is marked by provider as Legacy and you have not been
actively using the model in the last 30 days.
```

지정 모델이 구버전으로 분류되어 호출이 거부된 것이다. 활성 모델인 `global.anthropic.claude-sonnet-4-5-...`로 교체해 해결했다. 모델 ID를 `.env`로 분리해 둔 덕분에 설정 변경만으로 대응할 수 있었다.

### JSON 파싱 실패

03번 실행 시 다음 오류가 반복됐다.

```
JSON 파싱 실패: Expecting value: line 1 column 1 (char 0)
```

분류 결과 자체는 정확했으나, 모델이 응답을 ` ```json … ``` ` 코드블록으로 감싸 `json.loads()`가 첫 문자부터 실패했다. 코드블록을 제거하는 `strip_json_fence()`를 추가해 03~05번에 적용하니 정상 파싱됐다. 프롬프트로 "코드블록 금지"를 지시해도 항상 지켜지지는 않으므로, 코드 레벨의 방어 처리가 필요하다. 더 엄격한 검증은 이후 Pydantic으로 다룬다.

### operation_type 값 불일치

05번에서 조회 명령은 정상 생성됐으나 판정이 "변경 작업"으로 나왔다. 모델이 `operation_type`을 `read_only`가 아닌 `read`로 응답했기 때문이다. 원인은 05번 프롬프트에 (03번과 달리) 허용값 목록이 빠져 있었던 것이다. 허용값을 명시하자 조회 요청이 정확히 `read_only`로 분류됐다. 모델은 허용 범위를 모르면 유사한 다른 값을 생성하므로, 허용값을 명확히 지정하는 것이 중요하다.

## 정리

이번 실습에서 확인한 내용은 두 가지로 요약된다.

첫째, 파운데이션 모델은 프롬프트 구성만 바꿔도 여러 역할을 수행한다. 동일한 Claude 모델이 로그 분석기, 요청 분류기, 명령 생성기로 동작했으며 코드 구조는 거의 동일했다.

둘째, LLM에 판단은 맡기되 실행은 맡기지 않는 설계가 운영 자동화에서 중요하다. 조회는 명령을 생성하되 변경 작업은 승인을 거치게 한 구조가 이를 뒷받침한다.

또한 설정 분리와 코드 레벨 방어 처리가 실제 환경 차이(프로파일, 모델 ID, 응답 형식)에 대응하는 데 어떻게 기여하는지 확인했다. 다음 단계에서는 Pydantic을 사용한 응답 검증을 이어서 정리한다.
