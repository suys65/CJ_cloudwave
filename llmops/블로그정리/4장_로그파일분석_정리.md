# 로그 파일 분석 자동화: 운영자의 반복 작업을 Python으로 옮기기

> 수만 줄의 로그를 눈으로 훑는 대신, 규칙적인 검색·필터링·집계를 코드에 위임하는 방법을 정리했다. 텍스트 로그부터 JSON 로그까지, 그리고 마지막엔 함수로 분리된 자동화 스크립트 한 벌을 완성한다.

---

## 왜 자동화인가

운영 환경에서 장애가 발생하면 가장 먼저 확인하는 것이 로그다. "특정 시간대에 500 오류가 났는가", "어떤 IP가 비정상적으로 많이 요청했는가", "인증 실패가 늘었는가" 같은 질문에 대한 1차 근거가 전부 로그에 있기 때문이다.

문제는 **규모**다. 로그 10줄은 눈으로 `ERROR`를 찾으면 되지만, 웹 서버는 하루에 수만~수백만 줄을 쌓는다. 사람이 직접 훑는 것은 비효율적이고 실수도 잦다. 그런데 운영자가 로그에서 하는 작업은 대부분 정해져 있다.

- `ERROR` / `WARN` 로그만 추려내기
- 상태코드 `4xx`, `5xx` 개수 세기
- 특정 IP·URL의 요청 횟수 확인
- 잘못된 JSON 줄 걸러내기
- 오류 로그만 별도 파일로 저장

**반복적이고 규칙적인 작업**이라는 것 — 이게 자동화의 신호다. 이런 작업일수록 코드로 옮겼을 때 이득이 크다.

---

## 로그의 두 가지 형태

자동화 코드를 짜기 전에, 대상이 되는 로그가 어떤 구조인지 알아야 한다. 실무에서 만나는 로그는 크게 두 형태다.

### 텍스트 로그 — 사람이 읽기 좋다

```
2026-04-20 10:01:15 ERROR database connection failed
```

`날짜 시간 로그레벨 메시지` 순서의 문자열이다. 사람 눈에는 편하지만, **프로그램이 값을 꺼내려면 문자열을 잘라야 한다.** 위 줄에서 로그 레벨만 뽑으려면 공백으로 나눈 뒤 세 번째 조각(`ERROR`)을 집어야 한다.

### JSON 로그 — 프로그램이 다루기 좋다

```json
{"time":"2026-04-20T10:01:15","level":"ERROR","message":"database connection failed"}
```

한 줄이 하나의 JSON 객체다(이런 형식을 **JSON Lines** 또는 **NDJSON**이라 부른다). 문자열을 자를 필요 없이 `log["level"]`처럼 **키로 직접 접근**할 수 있다.

> **정리:** 텍스트 로그는 사람이 보기 좋고, JSON 로그는 프로그램이 분석하기 좋다. 어느 쪽을 다루느냐에 따라 코드의 파싱 전략이 달라진다.

여기에 더해, 웹 서버가 남기는 **액세스 로그**는 별도의 정형화된 형식을 쓴다.

```
127.0.0.1 - - [20/Apr/2026:10:01:15 +0900] "GET /api/items HTTP/1.1" 200 1234
```

IP · 시간 · 메서드 · 경로 · 상태코드 · 응답 크기가 정해진 위치에 나열된다. 위치가 일정하므로 정규표현식으로 원하는 값을 정확히 뽑아낼 수 있다.

## 핵심 작동 원리: 로그 분석 파이프라인

세부 코드가 아무리 늘어나도, 로그 자동화의 뼈대는 항상 같은 흐름을 따른다.

```
파일 열기 → 한 줄씩 읽기 → 조건 필터링 → 값 추출 → 집계 → 출력/저장
```

이 파이프라인을 이해하면 나머지는 각 단계를 정교하게 만드는 응용에 불과하다. 가장 기본형은 단 네 줄이다.

```python
with open("app.log", "r", encoding="utf-8") as file:
    for line in file:
        if "ERROR" in line:
            print(line.strip())
```

한 줄씩 뜯어보면 각 줄이 파이프라인의 한 단계에 대응한다.

| 코드 | 역할 | 왜 이렇게 쓰는가 |
| --- | --- | --- |
| `open(..., encoding="utf-8")` | 파일 열기 | 한글 로그를 대비해 인코딩을 명시한다 |
| `for line in file:` | 한 줄씩 읽기 | 파일 객체를 반복하면 메모리에 통째로 올리지 않고 줄 단위로 처리한다 |
| `if "ERROR" in line:` | 필터링 | 관심 있는 줄만 통과시킨다 |
| `line.strip()` | 정제 | 각 줄 끝의 줄바꿈 문자 `\n`을 제거한다 |

> **왜 `strip()`이 필요한가?** 파일에서 읽은 줄은 실제로는 `"... service started\n"`처럼 끝에 줄바꿈 문자가 붙어 있다. 그대로 출력하면 빈 줄이 하나씩 더 생긴다. `strip()`은 앞뒤 공백·탭·줄바꿈을 없애 출력을 깔끔하게 만든다.

## 문자열 검색의 한계, 그리고 정규표현식

`if "ERROR" in line` 방식은 빠르고 직관적이지만 **정확하지 않다.** 예를 들어 아래 줄은 실제 오류가 아니지만 `ERROR`라는 글자를 포함한다.

```
2026-04-20 10:02:10 INFO message=NOERROR
```

정확한 분석에는 두 가지 접근이 있다.

**첫째, 위치 기반 분리.** 로그 형식이 일정하다면 `split()`으로 나눈 뒤 특정 인덱스를 검사한다.

```python
level = line.split()[2]   # 세 번째 조각이 로그 레벨
if level == "ERROR":
    ...
```

**둘째, 정규표현식.** 상태코드·IP·경로처럼 **패턴이 있는 값**을 뽑을 땐 정규표현식이 정석이다. 액세스 로그에서 HTTP 상태코드를 추출하는 예를 보자.

```python
import re

line = '127.0.0.1 - - [...] "GET /api/items HTTP/1.1" 500 1234'
match = re.search(r'" (\d{3}) ', line)
if match:
    print(match.group(1))   # 500
```

여기서 핵심 개념 두 가지가 등장한다.

- **`r"..."` (raw string):** 정규표현식은 `\d` 같은 역슬래시를 많이 쓴다. `r`을 붙이면 파이썬이 역슬래시를 특수 처리하지 않아 패턴을 그대로 전달할 수 있다.
- **`group()` vs `group(1)`:** 괄호 `()`로 묶은 부분을 **그룹**이라 한다. `group()`은 매칭된 전체(`" 500 `)를, `group(1)`은 첫 번째 그룹인 상태코드(`500`)만 반환한다. **원하는 값만 괄호로 감싸서 콕 집어내는 것**이 정규표현식 추출의 핵심이다.

자주 쓰는 패턴을 정리하면 다음과 같다.

| 패턴 | 의미 |
| --- | --- |
| `\d+` | 숫자 1개 이상 (`500`, `1234`) |
| `\d{3}` | 숫자 정확히 3개 (상태코드) |
| `[^ ]+` | 공백이 아닌 문자 1개 이상 (경로 추출) |
| `( )` | 추출할 부분을 그룹으로 지정 |

> **`[^ ]+`의 감각:** 대괄호 안의 `^`는 "아닌 것"을 뜻한다. `[^ ]+`는 "공백이 아닌 문자가 하나 이상"이므로, `"GET /api/items HTTP/1.1"`에서 경로 `/api/items`처럼 **공백으로 둘러싸인 한 덩어리**를 정확히 잡아낸다.

## 집계: 딕셔너리에서 Counter로

로그 분석의 절반은 "몇 번 나왔는가"를 세는 일이다. 상태코드별 요청 수를 딕셔너리로 세면 이렇게 된다.

```python
status_count = {}
for line in file:
    code = re.search(r'" (\d{3}) ', line).group(1)
    if code not in status_count:   # 처음 등장하면
        status_count[code] = 0     # 0으로 초기화
    status_count[code] += 1
```

동작은 하지만 "키가 없으면 초기화"라는 준비 코드가 매번 붙는다. 파이썬 표준 라이브러리의 **`Counter`**는 이 초기화를 자동으로 처리한다.

```python
from collections import Counter

status_counter = Counter()
for line in file:
    code = re.search(r'" (\d{3}) ', line).group(1)
    status_counter[code] += 1      # 키가 없어도 0에서 시작
```

같은 목적이지만 코드가 짧고 의도가 분명하다. IP별·경로별 집계도 정확히 같은 패턴을 재사용한다 — 무엇을 키로 삼느냐만 바뀔 뿐이다.

| 집계 대상 | 키 추출 방법 |
| --- | --- |
| 상태코드별 | `re.search(r'" (\d{3}) ', line)` |
| IP별 | `line.split()[0]` (액세스 로그는 IP가 맨 앞) |
| 경로별 | `re.search(r'"[A-Z]+ ([^ ]+) HTTP/', line)` |
| 시간대별 | `line[:13]` (문자열 슬라이싱으로 "날짜 시" 단위) |

> **시간대별 집계의 트릭:** `2026-04-20 10:01:11 ...`에서 앞 13글자를 자르면 `2026-04-20 10`이 된다. 이걸 키로 쓰면 **시간 단위로 로그가 묶인다.** 날짜 파싱 라이브러리 없이도 되지만, 로그 형식이 바뀌면 어긋나므로 형식이 일정할 때만 안전하다.

## JSON 로그는 파싱이 곧 구조화다

JSON 로그는 `json.loads()`로 문자열을 딕셔너리로 바꾸는 순간 분석이 훨씬 견고해진다. 텍스트 로그의 `if "ERROR" in line`이 **부정확한 문자열 검색**이라면, JSON 로그는 **정확한 필드 비교**가 가능하다.

```python
import json

log = json.loads(line)
if log["level"] == "ERROR":                       # 정확히 level 필드만 검사
    print(f"time={log['time']}, message={log['message']}")
```

여기서 실무적으로 중요한 선택지가 하나 있다. 값에 접근하는 두 방식의 차이다.

- `log["level"]` — 키가 없으면 **에러가 발생**한다. 형식이 확실할 때 쓴다.
- `log.get("level")` — 키가 없으면 **`None`을 반환**한다. 형식이 들쭉날쭉할 수 있을 때 안전하다.

> 운영 로그는 모든 줄이 완벽한 형식이라는 보장이 없다. 그래서 실전에서는 `.get()`을 선호한다.

## 견고함이 자동화를 완성한다

여기까지가 "분석"이라면, 이제부터는 **자동화 스크립트로서의 품질**이다. 한 번 짜서 계속 돌릴 도구라면 다음 세 가지가 반드시 필요하다.

### 1. 깨진 데이터에도 멈추지 않기

로그 파일에는 형식이 깨진 줄이 섞일 수 있다. 잘못된 한 줄 때문에 전체 분석이 중단되면 자동화의 의미가 없다.

```python
try:
    log = json.loads(line)
except json.JSONDecodeError:
    print(f"{line_number}번째 줄은 JSON 형식이 아니어서 건너뜀")
    continue    # 이 줄만 건너뛰고 다음 줄 계속
```

> **운영 자동화의 철학:** 일부 데이터에 문제가 있어도 **전체 처리는 계속되어야 한다.** 문제가 된 줄이 몇 번째인지 남겨두면 나중에 원인을 추적할 수 있다.

### 2. 예상 가능한 오류에 사람이 읽을 메시지 주기

파일이 없을 때 파이썬의 기본 traceback을 그대로 보여주는 대신, 이해 가능한 메시지를 출력한다.

```python
try:
    with open("missing.log", "r", encoding="utf-8") as file:
        ...
except FileNotFoundError:
    print("파일을 찾을 수 없음")
```

### 3. 파일명을 코드에 박지 않기 — argparse

분석할 파일명이 매번 다른데 코드에 `"app.log"`를 고정하면 매번 코드를 고쳐야 한다. `argparse`로 실행 시점에 인자를 받으면 **코드 수정 없이 재사용 가능한 도구**가 된다.

```python
import argparse

parser = argparse.ArgumentParser(description="로그에서 키워드를 검색한다.")
parser.add_argument("--file", required=True, help="로그 파일 경로")
parser.add_argument("--keyword", required=True, help="검색할 키워드")
args = parser.parse_args()
```

```bash
python log_keyword_search.py --file app.log --keyword ERROR
```

덤으로 `argparse`는 `--help` 도움말을 자동 생성해준다.

## 오늘 정리한 것

로그 분석 자동화는 결국 하나의 뼈대(**읽기 → 필터링 → 추출 → 집계 → 출력**)를 점점 견고하게 다듬어가는 과정이다.

- **문자열 검색**(`in`)은 빠르지만 부정확하다 → **정규표현식**으로 패턴 기반 정밀 추출
- **딕셔너리 집계**의 초기화 번거로움 → **Counter**로 간결하게
- **텍스트 로그**의 위치 의존성 → **JSON 로그**는 파싱 즉시 필드 접근
- 깨진 데이터·없는 파일 → **예외 처리**로 멈추지 않게
- 고정된 파일명 → **argparse**로 재사용 가능한 CLI 도구로
- 길어진 코드 → **함수 분리**로 유지보수 가능하게

각 단계가 이전 단계의 한계를 보완하며 "장난감 스크립트"를 "운영에 투입 가능한 도구"로 끌어올린다. 다음 장에서는 이 로그가 로컬 파일이 아니라 **CloudWatch·S3 같은 클라우드 서비스**에 쌓여 있을 때 어떻게 접근하는지를 다룬다.
