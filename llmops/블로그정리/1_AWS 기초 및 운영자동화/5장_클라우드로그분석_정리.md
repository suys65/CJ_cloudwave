# AWS 클라우드 로그 분석: 로그가 로컬 디스크에 없을 때

> 앞 장에서는 서버에 저장된 로그 파일을 Python으로 직접 읽었다. 하지만 실무의 로그는 대개 로컬 디스크가 아니라 **CloudWatch Logs**나 **Amazon S3**에 쌓인다. 이번엔 클라우드에 흩어진 로그를 CLI·SQL·boto3로 끌어와 분석하는 두 갈래 파이프라인을 구성한다.

---

## 문제: `open()`으로 열 파일이 없다

6장의 코드는 전부 `open("app.log")`로 시작했다. 로그가 서버 디스크에 파일로 존재한다는 전제 위에 서 있었던 것이다. 그런데 실제 운영 환경에서는 이 전제가 잘 깨진다.

- EC2·컨테이너·Lambda는 로그를 로컬에 쌓지 않고 **CloudWatch Logs로 스트리밍**하는 경우가 많다.
- S3 버킷에 누가 접근했는지 같은 기록은 **S3 서버 액세스 로그**로 별도 버킷에 적재된다.
- 인스턴스는 오토스케일링으로 사라졌다 생겨나고, 로그만 중앙에 남는다.

즉, 6장에서 익힌 "읽기 → 필터링 → 추출 → 집계" 스킬을 실제로 쓰려면 그 **앞단**이 필요하다. **"로그가 어디 있는지 찾아서 끌어오는 법"** 말이다. 이 장의 주제가 바로 그것이다.

크게 두 갈래를 다룬다.

| 저장소 | 성격 | 조회 방법 |
| --- | --- | --- |
| **CloudWatch Logs** | 실행 중 애플리케이션이 실시간으로 밀어 넣는 로그 | CLI, Logs Insights, boto3 |
| **S3 + Athena** | S3에 파일로 적재된 대량 로그 | SQL (Athena) |

## 파이프라인 A — CloudWatch Logs

### 계층 구조부터 이해하기

CloudWatch Logs는 로그를 3단계 계층으로 저장한다. 이 구조를 알면 나머지가 쉽다.

```
로그 그룹 (Log Group)      예: /training/kytu7/application   ← 서비스 단위
   └ 로그 스트림 (Stream)   예: app-server-01                ← 인스턴스/프로세스 단위
        └ 로그 이벤트        {timestamp, message}            ← 로그 한 줄
```

로그 그룹은 "이 서비스의 로그 모음", 로그 스트림은 "그중 이 서버 하나가 남긴 흐름"이라고 보면 된다. 로그를 넣을 때는 이벤트 배열을 밀어 넣는다.

```json
[
  {"timestamp": 1784878946071, "message": "INFO method=GET path=/ status=200"},
  {"timestamp": 1784878949071, "message": "ERROR method=GET path=/api/users status=500"}
]
```

> **`timestamp`는 밀리초 단위 Unix epoch다.** 그리고 한 번에 넣는 이벤트는 반드시 **시간 오름차순**이어야 한다. 이 두 조건을 어기면 `PutLogEvents`가 조용히 거부하거나 순서가 뒤엉킨다.

### 조회의 두 얼굴: filter vs Insights

CloudWatch Logs를 조회하는 방법은 성격이 다른 두 가지다.

**`filter-log-events` — 원본을 그대로 가져온다.** 넣었던 message 문자열을 시간 범위로 잘라서 되돌려준다. 6장의 `if "ERROR" in line`에 해당하는 단순 문자열 필터(`--filter-pattern "ERROR"`)를 걸 수 있다.

```bash
aws logs filter-log-events \
  --log-group-name "/training/kytu7/application" \
  --filter-pattern "ERROR" \
  --start-time $START_MS --end-time $END_MS
```

**Logs Insights — SQL 비슷한 파이프 문법으로 가공한다.** 여기서부터가 흥미롭다. 6장에서 `Counter`로 손수 짜던 집계를 AWS가 대신 처리한다.

```
fields @timestamp, @message
| parse @message /status=(?<status_code>\d+)/   # message에서 상태코드 추출
| stats count(*) as request_count by status_code # 상태코드별 집계
| sort request_count desc
```

`parse`가 6장의 정규표현식 추출, `stats ... by`가 `Counter` 집계에 정확히 대응한다. 심지어 `stats count(*) by bin(5m)`처럼 **5분 단위 시간 버킷 집계**도 한 줄이다 — 이건 로컬 스크립트로 짜려면 꽤 번거로운 작업이다.

> **⚠️ 오늘 가장 많이 밟는 함정 — 시간 단위가 API마다 다르다.**
>
> | 기능 | 시간 단위 |
> | --- | --- |
> | `filter-log-events` | **밀리초** |
> | `put-log-events` | **밀리초** |
> | `start-query` (Logs Insights) | **초** |
> 
> `1770000000`(초)과 `1770000000000`(밀리초)은 1000배 차이다. 단위를 잘못 넣으면 "결과 없음"이 뜨거나 엉뚱한 시간대를 조회한다. 조회 결과가 비어 있을 때 가장 먼저 의심할 지점이다.

### 비동기 쿼리라는 새로운 패턴

Logs Insights는 **비동기**다. 쿼리를 시작하면 즉시 결과가 오지 않고 `queryId`만 받는다. 그 뒤 상태가 `Complete`가 될 때까지 폴링해야 한다. boto3로 자동화하면 이렇게 된다.

```python
response = client.start_query(logGroupName=LOG_GROUP,
                              startTime=start, endTime=end,   # 초 단위!
                              queryString=query)
query_id = response["queryId"]

while True:
    result = client.get_query_results(queryId=query_id)
    if result["status"] == "Complete":
        break
    time.sleep(2)   # 아직 Running이면 잠시 대기 후 재확인
```

**시작 → 폴링 → 완료 시 결과 저장.** 이 패턴을 기억해두자. 잠시 뒤 Athena에서 토씨 하나 안 틀리고 똑같이 재등장한다.

## 파이프라인 B — S3 서버 액세스 로그와 Athena

### 왜 로그 버킷을 따로 두는가

S3 서버 액세스 로그는 "내 버킷에 누가 언제 무엇을 요청했는지"를 기록한다. 핵심 설계는 **원본 버킷과 로그 버킷의 분리**다.

```
[원본 버킷]  ──PUT/GET/DELETE 요청──▶ 요청 발생
     │
     │  서버 액세스 로그 전달 (비동기, best-effort)
     ▼
[로그 버킷]
  ├─ s3-access-logs/    ← 분석 대상 로그
  └─ athena-results/    ← Athena 쿼리 결과
```

> **로그 버킷에는 다시 로깅을 켜지 않는다.** 로그가 쌓이는 것 자체도 S3 요청이므로, 로그 버킷에 또 로깅을 걸면 로그가 로그를 낳는 무한 반복이 생긴다.

로그 전달은 아무나 하는 게 아니라 S3의 로그 전달 서비스(`logging.s3.amazonaws.com`)가 대상 버킷에 객체를 쓰는 구조다. 따라서 로그 버킷 정책에 **"이 서비스 주체에게만, 이 경로에만 쓰기를 허용"**한다고 명시해야 한다.

```json
{
  "Principal": { "Service": "logging.s3.amazonaws.com" },
  "Action": "s3:PutObject",
  "Resource": "arn:aws:s3:::로그버킷/s3-access-logs/*",
  "Condition": {
    "ArnLike":     { "aws:SourceArn": "arn:aws:s3:::원본버킷" },
    "StringEquals":{ "aws:SourceAccount": "계정ID" }
  }
}
```

`Condition`의 두 줄이 보안의 핵심이다. **어느 원본 버킷**이 만든 로그인지(`SourceArn`), **어느 계정**인지(`SourceAccount`)를 못 박아 다른 곳에서 이 버킷에 로그를 흘려 넣지 못하게 막는다.

> **서버 액세스 로그는 실시간이 아니다.** best-effort 방식이라 요청 후 수 분에서 수 시간 뒤에야 로그 객체가 도착한다. 요청 직후 로그가 안 보인다고 설정 오류로 단정하면 안 된다. 그래서 실습에서는 **동일한 형식의 검증용 샘플 로그를 직접 업로드**해 파이프라인을 먼저 검증한다.

### 액세스 로그 한 줄의 정체

S3가 남기는 로그 한 줄은 27개 남짓한 값이 공백으로 나열된 **순수 텍스트**다.

```
sample-owner 원본버킷 [24/Jul/2026:01:20:30 +0000] 203.0.113.10 arn:...:user/student REQ0001 REST.PUT.OBJECT test/s3-test.txt "PUT /test/s3-test.txt HTTP/1.1" 200 - 0 27 15 10 "-" "aws-cli/2.0" -
```

이 줄 자체에는 "이게 IP다, 이게 상태코드다"라는 정보가 없다. 값이 공백으로 늘어서 있을 뿐이다. 이 텍스트를 조회 가능한 표로 바꾸는 것이 Athena의 역할이다.

> **실전 팁 — 공백 하나가 파싱을 깬다.** 오늘 샘플 로그를 만들 때 `sample-owner`와 버킷명 사이 공백이 빠져 있었다. 이러면 첫 두 컬럼(소유자·버킷명)이 한 덩어리로 붙어 정규식이 어긋난다. 검증용 샘플 단계에서 이런 형식 오류를 미리 잡아내는 것이 best-effort 로그를 기다리는 것보다 훨씬 빠르다.

### Athena의 핵심 원리: 스키마-온-리드(schema-on-read)

여기가 이 장에서 가장 중요한 개념이다. **Athena는 데이터를 복사하거나 옮기지 않는다.** 대신 S3에 이미 있는 파일 위에 "이렇게 읽어라"는 해석 규칙(스키마)만 씌운다. 이걸 **schema-on-read**라 부른다.

```sql
CREATE EXTERNAL TABLE s3_access_logs ( bucketowner STRING, bucket_name STRING, ... )
ROW FORMAT SERDE 'org.apache.hadoop.hive.serde2.RegexSerDe'
WITH SERDEPROPERTIES (
  'input.regex' = '([^ ]*) ([^ ]*) \\[(.*?)\\] ([^ ]*) ...'
)
LOCATION 's3://로그버킷/s3-access-logs/';
```

각 요소의 역할은 이렇다.

| 구문 | 역할 |
| --- | --- |
| `CREATE EXTERNAL TABLE` | S3 데이터를 **참조만** 하는 외부 테이블 생성 (데이터 복사 없음) |
| `RegexSerDe` | 정규식 그룹 하나 = 컬럼 하나로 텍스트 한 줄을 분해 |
| `LOCATION` | 분석 대상 파일들이 있는 S3 **접두사 경로** (파일이 아니라 폴더) |

> **6장과 이어지는 지점:** `RegexSerDe`의 정규식 각 괄호 `()`가 컬럼 하나에 대응한다. 6장에서 `match.group(1)`로 상태코드만 뽑던 그 그룹 개념이, 여기서는 SQL 엔진 레벨로 확장돼 **한 줄 전체를 27개 컬럼으로 동시에 분해**한다. 원리는 같고 규모만 커진 셈이다.

이 스키마가 등록되면, 그 순간부터 순수 텍스트 로그가 SQL로 질의 가능한 테이블이 된다.

### 익숙한 질문을 SQL로

6장에서 `Counter`와 `startswith("5")`로 하던 분석이 SQL에서 그대로 재현된다. **같은 질문, 다른 도구**다.

```sql
-- 상태코드별 집계 (6장의 Counter에 해당)
SELECT httpstatus, errorcode, COUNT(*) AS request_count
FROM s3_access_logs GROUP BY httpstatus, errorcode ORDER BY request_count DESC;

-- 5xx만 필터 (6장의 startswith("5")에 해당)
SELECT * FROM s3_access_logs WHERE httpstatus LIKE '5%';

-- IP별 요청 수 (6장의 ip_counter에 해당)
SELECT remoteip, COUNT(*) FROM s3_access_logs GROUP BY remoteip ORDER BY 2 DESC;
```

실제로 검증용 샘플 6줄에 대해 돌린 결과는 이랬다.

```
httpstatus  errorcode      request_count
200         -              2
403         AccessDenied   1
500         InternalError  1
204         -              1
404         NoSuchKey      1
```

`WHERE requester = '-'`로 익명 요청(인증 정보 없는 접근)을, `TRY_CAST(httpstatus AS INTEGER) >= 400`으로 4xx·5xx 오류를 한 번에 뽑아내는 등, 텍스트 파싱으로는 번거로운 조건도 SQL 한 줄로 처리된다.

> **로그 형식이 다르면 테이블도 나눈다.** S3 액세스 로그(공백 구분 텍스트)와 애플리케이션 로그(다른 필드 구조)를 같은 `LOCATION` 아래 섞으면, 정규식이 안 맞는 파일의 모든 컬럼이 `NULL`로 깨진다. 그래서 형식별로 **접두사(`s3-access-logs/`, `application-logs/`)와 테이블을 분리**한다. 오늘 앱 로그는 `ROW FORMAT DELIMITED FIELDS TERMINATED BY ' '`로 별도 테이블을 만들어 5xx·경로별 평균 응답시간을 따로 분석했다.

## 두 파이프라인이 결국 같은 모양인 이유

CloudWatch와 Athena는 전혀 다른 서비스지만, boto3 자동화 코드는 **거의 동일한 골격**이다.

```python
# Athena 자동화 — CloudWatch와 판박이
response = athena.start_query_execution(QueryString=QUERY,
             QueryExecutionContext={"Database": DATABASE},
             WorkGroup=WORKGROUP)
qid = response["QueryExecutionId"]

while True:
    state = athena.get_query_execution(QueryExecutionId=qid)["QueryExecution"]["Status"]["State"]
    if state == "SUCCEEDED":
        break
    if state in {"FAILED", "CANCELLED"}:
        raise RuntimeError(...)
    time.sleep(2)

result = athena.get_query_results(QueryExecutionId=qid)   # 결과 회수 → 파일 저장
```

**쿼리 시작 → 상태 폴링 → 완료 시 결과 저장.** 앞서 CloudWatch에서 본 패턴 그대로다. 서비스 이름과 메서드 이름만 바뀌었을 뿐, "비동기 쿼리를 자동으로 기다렸다 결과를 거둔다"는 틀은 동일하다. 이 골격을 한 번 익혀두면 다른 AWS 비동기 API에도 그대로 응용할 수 있다.

> **Athena는 결과를 어딘가 저장해야만 동작한다.** 쿼리를 돌릴 때마다 결과 CSV를 S3(`athena-results/`)에 쓰기 때문에, **작업 그룹(Workgroup)에 결과 저장 위치를 지정**해두지 않으면 `No output location provided` 오류로 쿼리가 아예 시작되지 않는다. 그리고 이 결과 경로는 반드시 분석 대상 로그 경로와 **분리**해야 한다 — 안 그러면 쿼리 결과 CSV가 다음 쿼리의 분석 대상에 섞여 버린다.

## 오늘 정리한 것

6장이 "로컬 파일에 있는 로그를 분석하는 법"이었다면, 7장은 **"로그가 클라우드 서비스 안에 있을 때 그것을 끌어오는 법"**이다.

- **CloudWatch Logs** — 로그 그룹/스트림/이벤트 계층에 실시간 로그를 쌓고, `filter-log-events`(원본)와 Logs Insights(집계)로 조회한다. **초/밀리초 단위 차이**가 흔한 함정.
- **S3 서버 액세스 로깅** — 원본 버킷의 요청 이력을 별도 로그 버킷에 적재한다. 로그 전달 서비스에만 쓰기를 허용하는 **버킷 정책**과, best-effort라는 **지연 특성**이 핵심.
- **Athena** — 데이터를 옮기지 않고 스키마만 씌우는 **schema-on-read**. `RegexSerDe`로 텍스트 로그를 SQL 테이블처럼 다루고, 6장의 집계·필터를 그대로 SQL로 재현한다.
- **boto3 자동화** — CloudWatch든 Athena든 "시작 → 폴링 → 결과 저장"이라는 **비동기 쿼리 패턴**은 동일하다.

로그가 로컬 디스크에서 클라우드로 옮겨가도, 결국 던지는 질문("어떤 오류가, 누가, 얼마나")은 6장과 똑같다. 바뀌는 것은 **그 질문을 어떤 도구로 던지느냐**뿐이다. `open()`과 `Counter`가 `filter-log-events`와 `GROUP BY`로 바뀌었을 뿐, 로그 분석의 본질은 그대로다.
